# The Messenger contract: one method per action, neutral types, capabilities

Accepted, 2026-11-06. Consolidates the Messenger decisions first recorded on 2026-11-03 (Instagram text through the Inbox-bound Messenger; conversation primitives and trusted Platform extensions), 2026-11-05 (one Messenger method per action) and the 2026-11-06 architecture hardening (neutral contract types, one media seam, one capability mechanism, ProfileReading, prebuilt Platform Messengers). This ADR states the whole current decision; the earlier ADRs it absorbed were deleted. Rules 1-6 keep their earlier numbers so existing references stay valid. How the contract is shaped (WhatsApp first, limits at construction) is [ADR-0028](0028-whatsapp-first.md).

## Context

Wappa's value is that a Host writes a conversation once and runs it on any connected Platform. The first Instagram pass broke this by adding Platform-named methods (`mark_seen`, `set_typing`, `send_quick_replies`, `send_buttons`, `send_card`) and an `InteractionWebhook` lane, so Hosts grew `if instagram` branches. Later the neutral contract still imported WhatsApp wire models (`MessageResult`, `InteractiveHeader`, `ListSection`), `capability()` existed twice, and three media seams grew around one.

## Decision

1. **One action, one method.** When an action exists on more than one Platform it has exactly one `IMessenger` method, and each adapter maps it onto its native API, even when that takes several provider calls. Examples: `mark_as_read(message_id, target, *, typing=False)` is a read plus typing indicator on WhatsApp and `mark_seen` then `typing_on` on Instagram; `send_button_message` is reply buttons on WhatsApp and a button template on Instagram, a media header sent first as its own attachment; `send_list_message` is a list on WhatsApp and quick replies on Instagram; `send_carousel` is a media carousel on WhatsApp and a generic template on Instagram (a video card shows its `poster_url` and opens the video on tap); `send_location` / `send_contact` are native on WhatsApp and text on Instagram; `send_sticker` is an image on Instagram.
2. **Inbound uses the same shapes.** A User's choice arrives as an `InboundMessageWebhook` with `get_interactive_selection()`, whether it came from a WhatsApp button or list reply, an Instagram quick reply or a postback. No Platform gets its own lane for an event another Platform already models.
3. **Adaptation emulates; it never drops meaning.** An adapter folds presentation its Platform cannot show into the message (Instagram has no footers or row descriptions) and emulates where it can (split long text, send a media header first). When a call cannot be honoured even by emulation, it raises `UnsupportedOperationError` before any provider call, naming the fix. Limits on structured values are enforced when the value is built ([ADR-0028](0028-whatsapp-first.md)), so a value that constructs is deliverable everywhere. Adapters document each mapping in their docstrings and in `docs/public-contract.md`.
4. **Exceptions are capabilities, not contract methods.** An action that only some Platforms have, with no reasonable mapping elsewhere, lives behind a focused, action-named interface in `wappa/domain/interfaces/`, filled into the adapter's `_capabilities` mapping in its constructor. `capability(kind)` / `require_capability(kind)` is the internal seam: implemented once in the `IMessenger` base, it looks a capability up by its interface only, never by a concrete adapter class, and is what adapters, the Messenger Pipeline, routes (`requires_capability(kind)`) and the Platform Messengers (rule 12) are built on. It is not Host API: Hosts reach capabilities as ready attributes (rule 12). A capability whose calls are messages (`ITemplateMessaging`, `IUserDataRequests`) is wrapped by `MessengerPipeline.capability()` so the message middleware still runs under its method names. This is the only extension mechanism. Event families that only one Platform emits (comments, mentions, calls) keep their own Universal Webhook types. Hosts check `supported_operations` or whether the Platform Messenger is `None`, never the Platform name.
5. **Typed contracts, never raw dicts.** Universal Webhooks expose Platform content through typed models; a shape with no model yet is named (`native_type`) and left `None`. Three bounded exceptions: `raw_webhook_data` (diagnostic, excluded from serialization, read through `get_raw_webhook_data()`), `CustomWebhook.raw_value` (the input of a Host-registered parser) and `CallWebhook.session` / `raw_call` until WhatsApp Calling is integrated. Inbound `nfm_reply` is a typed `FlowReply`. `send_contact` takes the neutral `ContactCard` (one or several).
6. **Separate responsibilities get separate contracts.** `IMessenger` only sends conversation messages, acknowledges them and reads the User's Platform profile. Media storage, Templates, comments and account connection each have their own interface, even when several Platforms implement it.
7. **Neutral values live in `wappa/domain/` only.** `MessageResult` (`wappa/domain/results.py`, `platform` required, `platform_response` the one native-evidence field), the interactive values in `wappa/domain/interactive.py` (`ReplyButton`, `UrlButton`, `MediaRef`, `InteractiveHeader`, `ListSection`, `ListRow`, `CardMedia`, `MessageCard`), `ContactCard`, `MediaRenditions` and the targets (`DirectMessage`, `PrivateReply`). `wappa.domain` imports no adapter, so a Platform implements `IMessenger` without importing WhatsApp. Neutral webhook and target types carry no Platform-named fields or validators: adapters without private replies reject `PrivateReply` at send. Field names copied from WhatsApp's shape (`UserBase.phone_number`, `bsuid`, `parent_bsuid`) are allowed by [ADR-0028](0028-whatsapp-first.md); their descriptions and validator messages stay Platform-neutral ("address evidence", not "WhatsApp evidence"). The neutral HTTP send request models live in `wappa/schemas/requests/`, beside `DeliveryRequest`, not in an adapter package.
8. **`supported_operations` is an explicit per-adapter set**, checked by a parity test against overridden methods plus qualifier tokens (`send_text:private_reply`); another test checks `MessengerPipeline` signatures against `IMessenger`. Every send runs through `MessengerPipeline`, whose middleware sees a `SendInvocation`.
9. **One media seam: `IMediaLibrary`.** `upload(source: Path | bytes, family, *, mime_type=None, filename=None) -> UploadResult`, `download(media_id, *, max_bytes=None) -> ReadResult[MediaBytes]`, `info(media_id)`, `delete(media_id)`, shaped like the WhatsApp Media endpoints, with `MediaFamily.STICKER`. `media_id` is exactly `webhook.message.media_id` on download and the reusable send ID on upload. Instagram stores a sticker as an image and raises `UnsupportedOperationError` for `info` and `delete` (no endpoint). WhatsApp's media handler is a concrete adapter-internal class behind the WhatsApp extension router; Instagram's attachment reader is private behind `InstagramMediaLibrary`.
10. **ProfileReading is a core method.** `resolve_platform_user_profile(user: UserBase) -> PlatformUserProfile` brings every fact the Platform provides about a User: WhatsApp maps the webhook evidence with no I/O, Instagram adds a Graph lookup with the Inbox token and returns the evidence with a failure outcome rather than raising. It is read-only and never called by Wappa during intake or dispatch; merging, persistence, caching and display-name policy belong to the Host. The Inbox's own business profile is a separate, later capability (`IInboxProfileReader`).
11. **Trusted extensions use `InboxCredentialAccess`.** A trusted backend adapter may receive a resolved bearer through this narrow seam to run extra provider operations; Wappa keeps encryption, current-credential resolution and invalidation. It does not make the directory or resolver a Host API. Wappa owns conversation mechanisms (comment intake, replies, private replies, content and media reads, comment-control primitives); Hosts own responses, moderation policy, AI, takeover and history.
12. **Prebuilt Platform Messengers; Hosts never build or look up a capability.** The runtime builds everything a Host calls, per dispatch. A capability every installed Platform provides is a ready attribute on `IMessenger` itself: `messenger.media` (`IMediaLibrary`, rule 9). Platform-only capabilities are ready on that Platform's Platform Messenger, the one allowed typed exception to a Platform-neutral handler: `WappaEventHandler.whatsapp: WhatsAppMessenger | None` and `WappaEventHandler.instagram: InstagramMessenger | None`, exactly one set to the dispatch's Platform and the other `None` (both `None` with no Messenger, as in a system cron). A Platform Messenger receives the core Messenger the runtime already built (the `MessengerPipeline`-wrapped one), forwards the whole `IMessenger` contract to it, so middleware runs as for `self.messenger`, and adds only its Platform's capabilities: WhatsApp `templates` (`ITemplateMessaging`), `send_location_request` and `send_contact_request` (`IUserDataRequests`); Instagram `comments` (`ICommentControls`), `content` (`IConversationContentReader`) and `history` (`IConversationHistoryReader`). It is never a second build of the Messenger. Each Platform's `PlatformEntry.build_platform_messenger(messenger)` in the Platform Registry builds it, and `with_context` binds it under the Platform's value, so shared code holds no Platform branch; the handler imports the two types under `TYPE_CHECKING` only. A Platform whose entry has no builder gets no Platform Messenger, with no shared-code edit. A new Platform-only capability becomes an attribute on its Platform Messenger, a new shared one an attribute on `IMessenger`; neither adds a Host-facing `capability()` call. The concrete adapters are `WhatsAppMessengerAdapter` and `InstagramMessengerAdapter`, internal to their adapter folders.

## Contract map

| Layer | Contract | WhatsApp | Instagram |
| --- | --- | --- | --- |
| Core (every Platform, adapted) | `IMessenger`: `send_text`, `send_image` / `send_video` / `send_audio` / `send_document`, `send_sticker`, `send_button_message`, `send_list_message`, `send_cta_message`, `send_carousel`, `send_location`, `send_contact`, `mark_as_read`, `resolve_platform_user_profile`; `transcript` on `send_video` / `send_audio` is middleware-only metadata that no adapter sends | native | adapted (rule 1) |
| Shared capability | `IMediaLibrary` (rule 9), ready as `messenger.media` (rule 12) | Media API | `message_attachments` + CDN reader |
| Platform capability | `ITemplateMessaging` as `self.whatsapp.templates` (later `IFlowMessaging`, `ICallControls`) | yes | — |
| Platform capability | `IUserDataRequests`: `self.whatsapp.send_location_request`, `self.whatsapp.send_contact_request` (HTTP `/specialized/send-location-request`, `/send-contact-request` behind `requires_capability`) | yes | — (a text prompt would not return the location or phone) |
| Platform capability | `ICommentControls`, `IConversationContentReader`, `IConversationHistoryReader` as `self.instagram.comments`, `.content`, `.history` | — | yes |
| Inbound (one shape) | `InboundMessageWebhook` (text, media, selections, reactions as `BaseReactionMessage`), `StatusWebhook`, `SystemWebhook`, `CustomWebhook`, `OutboundEchoWebhook`, `MessageUpdateWebhook`, `EntryReferral`, `HistoryThread` (pushed as `HistorySyncWebhook` or pulled through `IConversationHistoryReader`) | yes | yes |
| Inbound (one shape) | `InboxConnectionWebhook` | `account_offboarded` / `account_reconnected` | no emitter under Unified Login |
| Inbound, one Platform emits | `CallWebhook`, `ErrorWebhook`, contact sync / group / user action (WhatsApp); `IncomingCommentWebhook`, `MentionWebhook` (Instagram) | | |

Known gap: `send_reaction(message_id, emoji, target)` belongs on `IMessenger` (WhatsApp, Instagram and Telegram all have reactions) but is unimplemented; the user deprioritized it on 2026-11-06.

Instagram quote degradation stays inside the adapter: Instagram first sends `reply_to_message_id` as top-level `reply_to: {"mid": ...}`. If that call is rejected with HTTP 400 and Meta code `100/2534002`, it retries only that refused part once without `reply_to`, preserving the message and recipient. The returned result is the retry result, with `platform_response["wappa_reply_to"] = {"dropped": True, "error_code": "100/2534002"}` on success or failure. This evidence survives split text, media-caption and other multipart emulations alongside `wappa_parts`. Other errors and indeterminate outcomes never trigger quote fallback; accepted parts are never resent. Hosts use the same parameter on both Platforms without branching.

Every Platform implements one per-part result contract: `platform_response["wappa_parts"]` retains `message_ids` and `delivered` and adds ordered `parts` with role, exact text, Message ID and outcome. Single sends have one part; emulation flattens actual messages and planned parts skipped after a refusal. WhatsApp is normally one native part, including its caption; Instagram records its own caption follow-ups and split chunks. Shared formatting lives in `wappa/domain/message_parts.py`, while adapters own production and roles. Quote fallback remains one part with `reply_to_dropped`; indeterminate outcomes never become accepted or not_attempted. Future Platforms follow this contract rather than teaching Hosts to branch.

## Uniform evidence and discovery (0.34.6)

One shared action includes one serialized representation. Typed family projections own text/selection/media/reaction/context keys; native evidence stays behind its accessor. UserIdentity binds existing User ID policy, addresses and optional evidence to an Inbox Reference across Users, profiles, results and SSE. Adapters interpret opaque addresses and sanitize/order delivery candidates before I/O. MIME evidence is nullable, distinct from media family and historical nominal media_type.

MessagePart values and aggregate_outcome serialize independently of native evidence. Partial acceptance is distinct from a refusal with nothing accepted; per-part errors and retry delay survive. ErrorEvidence separates native code/subcode from neutral category and separates temporary from retry safety. Historical result codes and message_outcome remain unchanged. Static typed MessengerDiscovery reports operation/suboperation support, receipt scope, target kinds and accepted formats/sizes from adapter rules, available through Messengers and shared local HTTP discovery.

## Consequences

- Host code, Scores and Agents use one vocabulary on every Platform; a conversation built for Instagram runs on WhatsApp and the reverse, except for the Platform-only extras on `self.whatsapp` / `self.instagram`.
- Hosts write `self.messenger.send_text(...)`, `self.messenger.media.download(...)` and `self.whatsapp.send_location_request(...)` with nothing to build or look up; checking `self.whatsapp is None` replaces checking `capability()`.
- Adding a Platform means adapter mappings and tests against the existing contract. Adding a contract method needs a new reason: an action no existing method can express. Adding a capability is one interface, one adapter and one mapping entry, with no shared-code branch.
- The facade stays whole; no per-family interface split until real pressure shows it is too wide.
- Removed with no alias (see `CHANGELOG.md`): the Platform-named Instagram methods and the `InteractionWebhook` lane, `IMessenger.download_media` / `reply_comment` (now `IMediaLibrary` and `ICommentControls.reply_comment`), the Template methods on `IMessenger` (now `ITemplateMessaging`), `IMessenger.send_location_request` / `send_contact_request` (now `IUserDataRequests`), `capability()` lookup by concrete adapter class, `capability()` / `require_capability()` as documented Host API (now the prebuilt attributes of rule 12), the adapter class names `WhatsAppMessenger` / `InstagramMessenger` (now `WhatsAppMessengerAdapter` / `InstagramMessengerAdapter`; the old names are the Platform Messengers), the WhatsApp-housed `MessageResult`, interactive models and HTTP send request models, `InboundMessageWebhook.whatsapp`, `IMediaHandler`, `IAttachmentMediaReader` and the Instagram deauthorize route.

## Alternatives rejected

- Parallel Platform-named methods (every action maintained twice, Host branches).
- A `UserProfileReader` capability with one real adapter and one pass-through; promoting it waited on a second lookup, while one core method serves every Platform from evidence.
- Splitting `IMessenger` into per-family interfaces now (hypothetical seams).
- A Wappa-owned client for every extra provider call (expands Wappa's responsibility and displaces working Host adapters).
- A neutral `stream()` on `IMediaLibrary` before a caller and both adapters exist.
- Host-facing `require_capability(kind)` (the 2026-11-06 first hardening draft): every Host had to build its capability objects and import interfaces to reach a Platform feature.
- One `self.platform_messenger: IMessenger | None` handler attribute (untyped Platform extras) or Platform-only methods on `IMessenger` (rule 4).

## Structured per-part evidence (0.34.6 addendum)

Each MessagePart.content is a typed neutral snapshot of that part's actual structure, null for plain text. Adapters translate their final payload after emulation/media selection/upload into PartContent: buttons, quick replies, carousel elements, media, headers/footers, lists, contacts, locations, requests and native Template parameters. Normal JSON and historical wappa_parts carry it. Skipped plans remain not_attempted, and missing upload references are never invented. Hosts persist accepted parts' own text and content; a refused button structure cannot enter history just because an emulated header succeeded. This extends per-part evidence additively and does not change send signatures, native evidence exclusion or aggregate outcome semantics.
