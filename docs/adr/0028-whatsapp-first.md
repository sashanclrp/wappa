# WhatsApp First: neutral contracts mirror WhatsApp; limits are the minimum

Accepted, 2026-11-06 (user rule from the architecture-hardening review). Shapes every Platform-neutral contract described in [ADR-0025](0025-messenger-contract.md) and the HTTP request models in [ADR-0024](0024-outbound-http-routes-and-transports.md).

## Context

WhatsApp is Wappa's broadest Platform and the one most Hosts start on. When the neutral contract was first drawn alongside Instagram, it was narrowed toward the smaller Platform: button headers lost video and document, CTA headers became text only, carousel cards lost video, `send_document` dropped its caption, `send_contact` took one card, and list limits were checked per section instead of in total. Each narrowing silently removed a WhatsApp feature from every Host. Validating limits only at send time also meant a value could be built that one Platform could not deliver.

## Decision

1. **The shape follows WhatsApp.** Every Platform-neutral contract (the `IMessenger` methods, the neutral value types in `wappa/domain/`, and the HTTP request models fronting them) mirrors the WhatsApp Cloud API's seams and full feature set, so the WhatsApp adapter maps 1:1 and loses nothing. Examples: `InteractiveHeader` is text, or an image, video or document by `MediaRef` (`url` or `media_id`) with a document `filename`; `send_cta_message` takes the same header; `send_list_message` takes a text header; `CardMedia` is an image or video by URL (WhatsApp card headers accept a public link only) with an optional `poster_url`; `send_contact` takes several cards with optional phones; `send_document` carries its caption.
2. **Limits on structured values are the most restrictive across the installed Platforms**, enforced when the value is built, so a value that constructs is deliverable on every Platform with no send-time surprise. This covers button title, ID and count, list row title, description, ID and counts, section title, header text, footer, interactive body, list button text, card title, subtitle and count, CTA display text and carousel size, and WhatsApp's carousel card rules: `MessageCard.header` is required, a card has one URL button or 1-2 reply buttons (never a mix), and `check_carousel` requires the same button kind and count and the same header kind (all image or all video) on every card. No adapter repeats these checks at send. The limits live in one small constants block in `wappa/domain/interactive.py`, each constant commented with the per-Platform values it is the minimum of; plain arguments are checked by `check_button_message`, `check_list_message`, `check_cta_message` and `check_carousel`. There is no limits framework.
3. **Free-form text keeps WhatsApp's limit.** A `send_text` body or a media caption is divisible, so it keeps WhatsApp's limit (`TEXT_MAX` = 4096, `CAPTION_MAX` = 1024, in the same constants block, checked by `check_text` / `check_caption` in every adapter before any I/O and used by the HTTP request models) and a stricter Platform splits it into several messages (Instagram: 1000 UTF-8 bytes, on a word boundary when possible). Splitting preserves meaning, while a lower shared limit would remove WhatsApp capability. A split send returns one `MessageResult`: success only when every part was delivered, every part's message ID in `platform_response`, and a partial failure says how many parts were sent.
4. **Other Platforms emulate, and reject only when emulation is impossible.** Instagram sends a media header as its own message before the buttons or CTA template, folds text headers and footers into the body, flattens list sections into quick replies with their section titles and row descriptions folded into the body as a numbered menu, shares a document, audio or video URL it cannot attach as a text with the file name and link, and turns a video card into its poster image that opens the video on tap. When the meaning cannot be kept, the adapter raises `UnsupportedOperationError` before any I/O and names the fix. An action with no emulation on a Platform is a capability that Platform does not register instead (rule 6). The cases where emulation is impossible today: an Instagram video card without `poster_url`; a local file Instagram cannot attach (wrong format or over its size limit, with no link to share instead) or a sticker with no png/jpeg/gif/webp rendition, or a WebP as a local file (the upload endpoint fails on WebP; a WebP URL works); an Instagram `PrivateReply` over 1000 UTF-8 bytes; Instagram `IMediaLibrary.info` / `delete` (no endpoint); WhatsApp location and phone-number requests (`IUserDataRequests`), which Instagram does not provide because a text prompt would not return the data. The Consequences list them in full. A card is one visual unit, so card media is never sent apart from the card.
5. **No lowest common denominator.** A WhatsApp feature or field is never dropped because another Platform lacks it; only limits take the minimum. Optional fields that only another Platform uses (for example `MessageCard.default_url` on Instagram) stay, and WhatsApp ignores them.
6. **Shared code never imports WhatsApp classes or branches on Platform.** The WhatsApp shapes are copied into Wappa's own neutral types (the HTTP send request models live in `wappa/schemas/requests/`, each Platform's batch routing in `wappa/webhooks/<platform>/routing.py`), and a shared API takes the Platform explicitly instead of defaulting to WhatsApp (`register_webhook_field(..., platform=...)`, the media result models). `tests/test_third_platform_contract.py` fails on a Platform comparison or an adapter-package import outside the adapter folders. Platform-only features are reached through the prebuilt Platform Messengers `self.whatsapp` / `self.instagram` ([ADR-0025](0025-messenger-contract.md) rule 12, built on the internal `capability()` seam of rule 4), never through a Platform check.

## Consequences

- A Host writing for WhatsApp gets the whole Cloud API surface through the neutral contract, and the same code runs on Instagram through emulation.
- Some structured limits are lower than WhatsApp's own (for example a list row title is 20 characters because Instagram quick replies are 20, and a button-message body is 640 because the Instagram button template is 640). A Host that needs WhatsApp's higher structured limit on WhatsApp alone has no per-Platform escape hatch, by design.
- Adding a Platform with a stricter structured limit lowers the shared constant and is a breaking change listed in `CHANGELOG.md`.
- Instagram emulates media WhatsApp accepts: a document, audio or video URL in a format Instagram does not attach (`.docx`, `.xlsx`, `.txt`, `.mp3`, `.amr`, `.ogg`, `.3gp` …) is sent as a text with the file name and the link (one `MessageResult` with any caption, rule 3), http URLs pass through (Meta documents no scheme rule), upload names are transliterated to ASCII with the extension kept, and a list's section titles and row descriptions fold into the text as a numbered menu before the quick replies.
- The cases where Instagram emulation is impossible today, each raised before any Platform call: a local file (`Path` or `bytes`) in a format Instagram does not attach, since there is no link to share (`ValueError` telling the Host to convert it; Wappa does not convert media); a local file over Instagram's size limit (image 8 MB; audio, video and document 25 MB, against WhatsApp's 100 MB documents); a sticker with no png/jpeg/gif/webp rendition, or a WebP as a local file (the upload endpoint fails on WebP; a WebP URL works); a video card without `poster_url` (`UnsupportedOperationError`); a `PrivateReply` text over 1000 UTF-8 bytes (one message per comment); `IMediaLibrary.info` / `delete`; and `IUserDataRequests`. A Media ID is Inbox-scoped, so a WhatsApp Media ID is never an Instagram attachment_id; a Host serving both sets `MediaRef.url` as well. Format conversion and compression are the Host's job, outside Wappa's responsibilities (user decision, 2026-11-06); the formats to prepare per use are in `docs/backlog/in_progress/261103-instagram-conversations/references/media-formats.md`.

## Alternatives rejected

- The lowest common denominator shape (silently drops WhatsApp features for every Host).
- Per-Platform limits checked at send time (a value builds and then fails on one Platform).
- Lowering the free-form text limit to the strictest Platform (loses capability that splitting keeps).
- Silent truncation (loses meaning without telling the Host).
