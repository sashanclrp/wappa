# Inbound Platform webhooks (core interface 1)

## Summary

The runtime goes through one real seam: `processor_factory.get_processor(platform).create_universal_webhook(...)` (`wappa/core/inbound/runtime.py:309-312`), preceded by a per-Platform router (`route_whatsapp_payload` / `route_instagram_payload`). Both routers have the same signature `(payload, resolver) -> tuple[RoutedWebhookDelivery, ...]` (`wappa/core/inbound/instagram_routing.py:21-23`, `wappa/core/inbound/webhook_routing.py:50`), and both processors implement `create_universal_webhook`. That makes two adapters, so the seam is real, but nothing names it. A third Platform therefore edits the controller ternary, a hardcoded allow-set, a hardcoded supported-Platform set, the field-registry branch, the `wappa_app` wiring, and the runtime's SSE identity gate. Next to the live seam sits a dead parallel one: all of `wappa/webhooks/factory.py` (766 lines) and most of `wappa/processors/factory.py` (545 lines) have no production caller. The root `ARCHITECTURE.md` still tells contributors to register a new Platform in both. Neutral webhook types import no WhatsApp classes. The exception is the WhatsApp-only `InboundMessageWebhook.whatsapp` slot.

The verification re-opened every cited line and confirmed four auditor findings, some with corrections. The two dead-factory findings were merged. Two findings were refuted: the `CallWebhook.user_id` fallback is correct code, and the Meta callback authentication is correct shared design. The deauthorize route was handed to area 05. The proposed protocol was cut from seven members to four: `sse_identity`, `display_name` and `bind_field_registry` are not needed.

## Confirmed findings

### 01-1 Dead parallel inbound seam: SchemaFactory, both schema registries, PlatformDetector, WebhookFactory, ProcessorCapabilities

- **Files**: `wappa/webhooks/factory.py`, `wappa/processors/factory.py`, `wappa/processors/base_processor.py`, `wappa/webhooks/ARCHITECTURE.md`, `wappa/webhooks/CONTEXT.md`, `ARCHITECTURE.md`
- **Principle**: shallow-module (dead pass-through; also stale-doc)
- **Severity**: high
- **Breaking + public surfaces**: not breaking. `wappa.webhooks.factory`, `PlatformDetector`, `WebhookFactory`/`webhook_factory` and `ProcessorCapabilities` are not in `docs/public-contract.md`. The only external users of `wappa.processors.factory` are `processor_factory.get_processor` (`tests/test_meta_payload_fixtures.py:26,93`, `tests/test_instagram_conversations.py:606-608`) and `get_supported_platforms`.
- **Evidence**: `rg` for `SchemaFactory|schema_factory|webhooks.factory|message_registry|webhook_registry|WebhookFactory|PlatformDetector|get_processor_for_payload|get_processor_capabilities` outside the two factory files finds nothing in `wappa/` or `tests/`. The production callers of `processor_factory` are `get_processor` (`wappa/core/inbound/runtime.py:309`, `wappa/core/wappa_app.py:287,291`) and `get_supported_platforms` (`wappa/core/plugins/wappa_core_plugin.py:243`, `wappa/api/routes/webhooks.py:171,183,196`). `wappa/webhooks/factory.py` holds `MessageSchemaRegistry` (:23), `WebhookSchemaRegistry` (:206) with hardcoded Platform registration (:44, :225-232) and `SchemaFactory` (:300) with a `PlatformType.WHATSAPP` branch (:439). `SchemaFactory.create_universal_webhook` (:572-602) calls back into `processor_factory`, so the delegation is circular. `wappa/processors/factory.py` holds `PlatformDetector` (:16-160) with WhatsApp/Telegram/Teams/Instagram branches; its own comment at :99 says Meta signatures do not establish Platform identity. Its only callers are `get_processor_for_payload` (:266-305) and `WebhookFactory` (:377-540, built at :545 and never used). `ProcessorCapabilities` (`base_processor.py:21`) is referenced only inside `wappa/processors/`. The docs present this dead code as the entry point: `wappa/webhooks/ARCHITECTURE.md:36,94-95,106,116-117,174`, `wappa/webhooks/CONTEXT.md:33-35`, and the root `ARCHITECTURE.md:306-307`, which lists "Processor registration: `wappa/processors/factory.py` (Platform detection ...)" and "Schema registration: `wappa/webhooks/factory.py`" as required steps for a new Platform.
- **Deletion test**: deleting `wappa/webhooks/factory.py`, `PlatformDetector`, `get_processor_for_payload`, `get_processor_capabilities`, `WebhookFactory`/`webhook_factory` and `ProcessorCapabilities` breaks no production path or test. The complexity vanishes and reappears nowhere. Only `get_processor`/`_create_processor`/`get_supported_platforms` earn their keep, and 01-2 turns them into a registry.
- **Proposed fix**: delete the modules and classes above, along with the abstract `capabilities` property on `BaseWebhookProcessor` and its two implementations. Remove the matching rows from `wappa/webhooks/ARCHITECTURE.md`, `wappa/webhooks/CONTEXT.md`, and the root `ARCHITECTURE.md:306-307`. Rewrite step 2 of "Adding a message family" (`wappa/webhooks/ARCHITECTURE.md:174`) to say the WhatsApp processor's own handler table (`whatsapp_processor.py:103-107`) is the registration point. Keep the `BaseWebhook` / `BaseMessage` ABCs.
- **ADR conflict**: none. ADR-0010 (payload-derived routing, the URL names the Platform) already makes payload, URL and header detection redundant.

### 01-2 No named PlatformWebhooks seam: "which Platform?" is decided again in five places, against three disagreeing supported-Platform lists

- **Files**: `wappa/api/controllers/webhook_controller.py`, `wappa/processors/factory.py`, `wappa/core/wappa_app.py`, `wappa/core/plugins/wappa_core_plugin.py`, `wappa/api/routes/webhooks.py`, `wappa/core/inbound/webhook_routing.py`, `wappa/core/inbound/instagram_routing.py`, `wappa/processors/base_processor.py`, `ARCHITECTURE.md`
- **Principle**: missing-interface
- **Severity**: high
- **Breaking + public surfaces**: not breaking. `POST/GET /webhook/inboxes/{platform}`, the `WappaEventHandler` lanes, and the `/platforms` and status responses keep their shape. `BaseWebhookProcessor` and `processor_factory` are internal.
- **Evidence**: (a) The controller's supported set is every `PlatformType` (`webhook_controller.py:53`), so `GET /webhook/inboxes/telegram` answers a Meta challenge (:74-90). POST then re-filters with a hardcoded `{WHATSAPP, INSTAGRAM}` (:116) and picks the router with a ternary (:137-141). (b) `processor_factory._create_processor` is an if/elif with lazy imports plus Telegram/Teams branches that only raise "not implemented" (`processors/factory.py:231-263`). `get_supported_platforms` is a separate hardcoded set (:307-319) that `_create_processor` does not derive from. The application therefore has three supported-Platform lists that can drift. (c) `wappa_app.py:287-293` fetches each processor by name, checks `WhatsAppWebhookProcessor` with `isinstance`, and probes `set_field_registry` on Instagram with `getattr`, although both adapters define it (`whatsapp_processor.py:98`, `instagram_processor.py:136`). (d) `wappa_core_plugin.py:243-250` hardcodes a label dict and a LEGACY-mode `{WHATSAPP}` filter. (e) `RoutedWebhookDelivery` and `PayloadRoutingError`, which both routers share, live in the WhatsApp-specific `webhook_routing.py` (:22, :37) and Instagram imports them from there (`instagram_routing.py:18`). (f) `BaseWebhookProcessor` (`base_processor.py:70-173`) makes `parse_webhook_container`, `get_supported_message_types`, `create_message_from_data` and `create_status_from_data` abstract. They are called only by each adapter on itself (`whatsapp_processor.py:333,498,531,757,883`, `instagram_processor.py:185`), and Instagram's `create_status_from_data` raises `NotImplementedError` (`instagram_processor.py:169-174`), which violates ISP. (g) The root `ARCHITECTURE.md:304` lists "the Platform branch in `webhook_controller.py` (allowed set and payload router choice)" as a required edit for a new Platform.
- **Deletion test**: the five call sites each re-decide the Platform. A registry of adapters with one small protocol pulls that decision into a single lookup, so the five branches collapse into `registry[platform]`. Two real adapters already exist, so this seam is real, not hypothetical.
- **Proposed fix**: add the `PlatformWebhooks` protocol described in the Interface proposal and a composition-root builder that returns `dict[PlatformType, PlatformWebhooks]`. The builder replaces `ProcessorFactory`: it constructs each adapter with the `FieldHandlerRegistry`, which removes the `set_field_registry` mutation and the `wappa_app` wiring. The controller looks up the adapter (400 if missing, for both GET and POST) and calls `adapter.route(...)`. The runtime calls `adapter.translate(...)`. The status route, the `/platforms` route and the core plugin read `registry.keys()`, and the plugin logs `platform.value` or keeps a cosmetic label map. Move `RoutedWebhookDelivery` and `PayloadRoutingError` to a neutral `wappa/core/inbound/delivery.py`. Shrink `BaseWebhookProcessor` to `platform` + `translate` (or drop it for the Protocol) and make the parse/build helpers private to each adapter. Update `ARCHITECTURE.md:300-307` so a new Platform means one adapter package plus one registry entry.
- **ADR conflict**: none. ADR-0002 (the Inbound Runtime orchestrates, processors stay pure) is kept because `route` does credential I/O and `translate` stays pure. ADR-0010 is kept because authentication still runs before parse, in the controller.

### 01-3 Inbound runtime gates SSE identity on WHATSAPP and guesses phone vs BSUID from identifier shape

- **Files**: `wappa/core/inbound/runtime.py`, `wappa/core/sse/context.py`
- **Principle**: platform-branch
- **Severity**: medium
- **Breaking + public surfaces**: not breaking. SSE `bsuid` / `phone_number` stay the same for WhatsApp, and Instagram stays `None`.
- **Evidence**: `runtime.py:393` reads `if webhook.platform is not PlatformType.WHATSAPP: return fallback_user_id, None, None`. The gate exists because `classify_meta_identifier` (`sse/context.py:135-148`) treats anything that is not BSUID-shaped as a phone, so an Instagram scoped ID would be misreported as a phone number. The runtime applies that shape guess to `StatusWebhook.user_id` (:404-408) and to the fallback (:412-413), even though the neutral types already carry explicit evidence. `UserBase` has `bsuid`/`phone_number`, read by `derive_identifiers` (`sse/context.py:151-162`), and `platform_user_id` is mutually exclusive with them (`base_components.py:102-110`). `StatusWebhook` has `recipient_bsuid` and `recipient_phone_id`. `CallWebhook` has `bsuid`/`phone_number`. `_enrich_status_user_id` (:416-437) is keyed on evidence (`recipient_phone_id` empty means a no-op), so it is not a Platform branch.
- **Deletion test**: delete the Platform gate and the shape guessing, and read the evidence fields the adapters already fill. The branch vanishes and nothing reappears elsewhere, because each adapter already decides which evidence it fills.
- **Proposed fix**: rewrite `_derive_sse_identity` to read only evidence. For `InboundMessageWebhook`/`SystemWebhook` with a user, use `derive_identifiers(user)`. For `CallWebhook`, use `(bsuid, phone_number)`. For `StatusWebhook`, use `(recipient_bsuid, recipient_phone_id or None)`. Otherwise return `(None, None)`. Drop the `PlatformType` check, and drop the `classify_meta_identifier` calls from the runtime. Do **not** add an `sse_identity` method to the Platform protocol: the evidence is already neutral data, and a protocol method would be a hook that only WhatsApp fills. Separately, `sse_event_scope(platform: str = "whatsapp")` (`sse/context.py:172`) defaults to a Platform; area 09 owns that default.
- **ADR conflict**: none (ADR-0019 makes identity evidence explicit on `UserBase`).

### 01-4 Neutral InboundMessageWebhook carries a WhatsApp-only sender slot that duplicates UserBase

- **Files**: `wappa/webhooks/core/webhook_interfaces/universal_webhooks.py`, `wappa/webhooks/core/webhook_interfaces/__init__.py`, `wappa/processors/whatsapp_processor.py`, `wappa/webhooks/core/webhook_interfaces/base_components.py`, `tests/test_whatsapp_processor_user_base.py`
- **Principle**: platform-leak
- **Severity**: medium
- **Breaking + public surfaces**: breaking. `InboundMessageWebhook` is public (`docs/public-contract.md:280`, `from wappa.webhooks import InboundMessageWebhook`), so a Host can read `.whatsapp` today. `WhatsAppIncomingWebhookData` is exported from `wappa.webhooks.core.webhook_interfaces` (`__init__.py:62,77`). The CHANGELOG needs a break entry.
- **Evidence**: `universal_webhooks.py:61-90` defines `WhatsAppIncomingWebhookData` (`wa_id`, `bsuid`, `parent_bsuid`, `username`, `country_code`) inside the neutral module, and `InboundMessageWebhook.whatsapp` (:108-111) carries it. The only writer is `whatsapp_processor.py:774` through `_create_whatsapp_incoming_data` (:1430-1451). That helper rebuilds from contacts the same values that `UserBase` already holds (`base_components.py:64-91`: `phone_number`, `bsuid`, `parent_bsuid`, `username`, `country_code`). Correction to the auditor: there is one reader, a test (`tests/test_whatsapp_processor_user_base.py:101-103`); no reader exists in `wappa/`. Instagram never fills it. A third Platform would copy the pattern and add `.telegram`. Related doc drift: `base_components.py:3-6`, `:22` and `:51` describe the neutral model as "based on WhatsApp's ... structure".
- **Deletion test**: delete the field, the class, the helper and the export. The only fallout is a test assertion that moves to `webhook.user.bsuid` / `webhook.user.phone_number`. Nothing reappears.
- **Proposed fix**: remove `WhatsAppIncomingWebhookData`, `InboundMessageWebhook.whatsapp`, `_create_whatsapp_incoming_data` and the export, and update the test to read `webhook.user`. Keep the `UserBase` / `StatusWebhook` phone/bsuid fields, which are honest identity evidence that Hosts use under ADR-0019. Fix the docstrings so they call these fields Platform-optional identity evidence instead of describing the model as "based on WhatsApp". Do not introduce a per-Platform union.
- **ADR conflict**: none. The clean-cut release norm applies: no alias.

### 01-5 FieldHandlerRegistry owns a Platform branch and defaults every Platform-qualified call to WhatsApp

- **Files**: `wappa/core/events/field_registry.py`, `wappa/core/wappa_app.py`, `wappa/core/factory/wappa_builder.py`
- **Principle**: platform-branch
- **Severity**: low
- **Breaking + public surfaces**: breaking only if the default is removed: `register_webhook_field(..., platform=PlatformType.WHATSAPP)` on `Wappa` (`wappa_app.py:495-501`) and `WappaBuilder` (`wappa_builder.py:246-252`), documented at `docs/public-contract.md:71`.
- **Evidence**: `_builtin_fields` (`field_registry.py:88-93`) branches on `INSTAGRAM` and otherwise returns WhatsApp's `BUILTIN_WEBHOOK_FIELDS`. `_REGISTRABLE_PLATFORMS` (:96) is a hardcoded pair. `FieldHandler.platform`, `register`, `get` and `fields` default to `WHATSAPP` (:85, :111, :160, :164), and `__contains__` is WhatsApp-only (:169-173). Correction to the auditor: an unlisted Platform does **not** silently get WhatsApp's built-ins, because `register` rejects it at :135-138 before `_builtin_fields` runs (:139). The real cost is that a third Platform edits this core file, which is a third copy of the supported-Platform list.
- **Deletion test**: once each adapter exposes `builtin_fields` (Interface proposal), the branch and the allow-set are derived from the adapter registry: registrable means present in the registry. The knowledge moves to the module that already defines it (`webhooks/instagram/models.py` `INSTAGRAM_BUILTIN_FIELDS`).
- **Proposed fix**: construct `FieldHandlerRegistry` with `builtin_fields: Mapping[PlatformType, frozenset[str]]` taken from the adapter registry at the composition root, and delete `_builtin_fields` and `_REGISTRABLE_PLATFORMS`. Make `platform` required on `get`/`fields`; the internal callers already pass it (`event_dispatcher.py:373`, `instagram_processor.py:179,500`). Removing the `WHATSAPP` default from the public `register_webhook_field` is optional. If it is removed, record it as a clean-cut break in the CHANGELOG. `__contains__` should go, or take the platform explicitly.
- **ADR conflict**: none.

- `wappa/core/inbound/runtime.py:_enrich_status_user_id` (:416-437): keyed on the presence of `recipient_phone_id` evidence and the cache backend, with no Platform gate. For Instagram it is a natural no-op.

- `wappa/processors/whatsapp_processor.py` and `wappa/processors/instagram_processor.py`: pure translation with no I/O, which matches ADR-0002 and `ARCHITECTURE.md:320`. The 1584-line WhatsApp processor is the adapter body, not shared code.
- `wappa/processors/factory.py:231-239` lazy imports: a Platform branch is acceptable at a composition root. Only its if/elif shape and the separate hardcoded set are flagged (01-2b).
- `wappa/webhooks/core/base_message.py`, `wappa/webhooks/core/webhook_interfaces/conversation_webhooks.py`: no WhatsApp type is imported, and the WhatsApp/Instagram mentions are docstrings only.
- `UserBase` phone/bsuid/`platform_user_id` (`base_components.py:64-110`): `phone_number` defaults to `""`, `platform_user_id` is mutually exclusive with WhatsApp evidence, and `delivery_addresses()` is neutral. A future Platform can fill the model, as the fake Telegram mapping test shows (`tests/test_webhook_schema_ownership.py:441-473`). Only the docstrings are WhatsApp-flavoured (01-4).
- `wappa/core/events/webhook_factory.py` `generate_webhook_url(platform)` iterates `PlatformType`. The `generate_whatsapp_*` helpers are thin and neutral enough.
- `IWebhookProcessor` (`wappa/domain/interfaces/webhook_processor.py`) and `IExternalWebhookContextResolver`: these form the External Webhook Sources seam (ADR-0012), which Hosts implement. They are not the Platform inbound seam, and having no in-repo adapter is expected for a Host extension point.
- `webhook_controller.py:119-130` authenticate-then-parse ordering and the 400/503/500 error mapping (:142-185): this is the ADR-0010 contract and it is correct.
- Echo origin proof via `ISentMessageRegistry` in the runtime: ADR-0018 places it in the Inbound Runtime, and it branches on origin evidence, not on Platform.

## Interface proposal

`PlatformWebhooks` is a Protocol in a neutral module (for example `wappa/core/inbound/platform_webhooks.py`, next to the neutral `RoutedWebhookDelivery` moved out of `webhook_routing.py`). Two real adapters (WhatsApp, Instagram) justify it. It has four members, and each one replaces a branch that exists today:

```python
class PlatformWebhooks(Protocol):
    platform: PlatformType
    builtin_fields: frozenset[str]          # replaces field_registry._builtin_fields + _REGISTRABLE_PLATFORMS

    async def route(
        self, payload: dict[str, Any], resolver: IInboxCredentialResolver
    ) -> tuple[RoutedWebhookDelivery, ...]: ...   # today's route_whatsapp_payload / route_instagram_payload; may raise PayloadRoutingError and the Inbox Directory 503 family

    async def translate(
        self, payload: dict[str, Any], *, inbox_id: str
    ) -> UniversalWebhook: ...                    # today's create_universal_webhook; pure, no I/O
```

The registry is a plain `Mapping[PlatformType, PlatformWebhooks]`, built once at the composition root by `build_platform_webhooks(field_registry)`, which replaces `ProcessorFactory`. Adapters receive the `FieldHandlerRegistry` in their constructor, so there is no `bind_field_registry`/`set_field_registry` mutation. The set of installed Platforms is `registry.keys()`. That one set serves the controller's GET and POST checks, `/webhook/platforms`, the status route, and the core plugin's URL log, and it replaces the three lists that drift today. A missing key is a 400 in the controller.

The protocol leaves out the following on purpose. `sse_identity` is excluded because SSE identity is read from neutral evidence fields (01-3). `display_name` is excluded because it is cosmetic: use `platform.value` or keep the label map in the plugin. `authenticate` is excluded because both Platforms use `MetaCallbackAuthenticator`; add it only when a non-Meta Platform exists (rejected 01-8). Per-message-type registries are excluded because each adapter keeps its own handler table privately. `route` and `translate` stay two methods, not one, because ADR-0002 has the runtime run admission and echo proof between I/O routing and pure translation. Each method is one action in the ADR-0016 spirit.

Platform-only inbound lanes (WhatsApp Calls, Instagram Comments) stay as Universal Webhook classes that only their adapter emits, with no capability flag and no shared-code branch. After this change, a third Platform is one adapter package (`webhooks/<platform>/` models, processor and routing) plus one registry entry. The controller, the runtime, `field_registry`, `wappa_app` and the core plugin need no edits.
