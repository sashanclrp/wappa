# Templates, Flows and Calls (WhatsApp-only capabilities)

## Summary

The capability mechanism is already the right shape for WhatsApp-only features. `IMessenger.capability()` / `require_capability()` is the only discovery path, `ITemplateMessaging` is not an `IMessenger` method (ADR-0016 contract map, `docs/adr/0016-one-messenger-method-per-action.md:35`), and `CallWebhook` is a single-Platform event family that ADR-0016 rule 4 (line 17) allows. Verification kept three of the auditor's nine findings, two of them merged. (1) `OutboundRuntime`, the Host's outbound Messenger factory for every Platform, sits in the Template-named `template_transport.py`. (2) `InboxTemplateTransport` is keyed by a bare `inbox_id`, reaches the private `OutboundRuntime._messenger` that hardcodes `InboxRef.whatsapp`, and the route layer works around this with a Platform-name gate (`whatsapp_only`). (3) Flows have no contract in either direction (inbound `nfm_reply` becomes Unsupported, outbound does not exist). The other findings were rejected: a pipeline registry for sending capabilities (premature with one such capability), collapsing the three Template methods (contract churn that ADR-0016 does not ask for), Calls SSE identity (out of area and not Calls-specific) and a capability lookup table (the auditor itself says do nothing). No neutral interface should be invented for Templates, Flows or Calls: each has exactly one adapter.

## Confirmed findings

### 07-2 OutboundRuntime (the outbound Messenger factory for every Platform) lives in the Template module

- **Files:** `wappa/messaging/template_transport.py`, `wappa/api/dependencies/inbox_context.py`, `docs/public-contract.md`
- **Principle:** SRP
- **Severity:** low
- **Breaking:** no for the public `wappa.messaging.OutboundRuntime` import (re-exported at `wappa/messaging/__init__.py:85`, listed at `docs/public-contract.md:886`). The deep path `wappa.messaging.template_transport.OutboundRuntime` changes; it is not named in the contract. Public surfaces: `wappa.messaging.OutboundRuntime`, the deep module path.
- **Evidence:** The module docstring calls it the Template boundary (`template_transport.py:1-6`). `OutboundRuntime` (`template_transport.py:452-566`) owns `from_app` wiring, `messenger(inbox_ref)` for any Platform (531-546), `evict_inbox` (548-555) and `templates()` (515-529). Only `templates()` and `_messenger` are about Templates. Every send route for both Platforms reaches it through that module: `InboxExecutionContext.messenger` imports `OutboundRuntime` from `wappa.messaging.template_transport` (`inbox_context.py:151-161`), and `get_inbox_messenger` / `requires_capability` build on it (`inbox_context.py:310-335`). The contract documents `OutboundRuntime.from_app(app).messenger(inbox_ref)` as the Host-initiated send path (`docs/public-contract.md:69`).
- **Deletion test:** Deleting `OutboundRuntime` would push MessengerFactory and pipeline construction into every Host and route, so the module earns its keep. What fails is its location: the generic Messenger half is filed under one Platform's capability.
- **Proposed fix:** Move `OutboundRuntime` (constructor, `from_app`, `messenger`, `evict_inbox`) to `wappa/messaging/outbound_runtime.py`. Keep `templates()` on it as a one-line factory returning `InboxTemplateTransport`, which stays in `template_transport.py` with the request and outcome models. Update the two imports in `inbox_context.py` and the re-export in `wappa/messaging/__init__.py`. No alias at the old path (clean cut); note the moved deep path in CHANGELOG.
- **ADR conflict:** none. ADR-0006 names `OutboundRuntime` as the Template factory; adjust its wording, no reversal.

### 07-4 InboxTemplateTransport is keyed by a bare inbox_id and hardwired to WhatsApp, so routes gate on the Platform name (merges 07-4 and 07-5)

- **Files:** `wappa/messaging/template_transport.py`, `wappa/api/dependencies/inbox_context.py`, `wappa/api/routes/whatsapp/whatsapp_templates.py`
- **Principle:** DIP
- **Severity:** low
- **Breaking:** yes, small. `OutboundRuntime.templates(inbox_id)` becomes `templates(inbox_ref)`, and the `InboxTemplateTransport` constructor stops taking `runtime=`. Public surfaces: `OutboundRuntime.templates` (`docs/public-contract.md:695`), `InboxTemplateTransport`, `InboxExecutionContext.template_transport`; `POST /templates/send-*` behaviour does not change.
- **Evidence:** `InboxTemplateTransport.send` calls the private `self._runtime._messenger(self.inbox_id, ...)` (`template_transport.py:404-407`). `_messenger` duplicates the public `messenger()` except that it builds `InboxRef.whatsapp(inbox_id)` (`template_transport.py:557-566` vs `531-546`). Because the transport cannot be given an `InboxRef`, the route layer has to stop non-WhatsApp Inboxes by name: `template_transport()` calls `whatsapp_only(self.inbox_ref, "Templates")` (`inbox_context.py:138-149`), and `whatsapp_only` itself says it is for places where "no capability interface exists yet" (`inbox_context.py:94-99`). For Templates a capability does exist, and `requires_capability` already gates by `messenger.capability(kind)` (`inbox_context.py:318-335`). There is also a latent outcome bug: `_send_request` calls `require_capability(ITemplateMessaging)` inside the send `try` (`template_transport.py:573`, `421-440`). `UnsupportedOperationError` subclasses `NotImplementedError` (`wappa/domain/messaging_targets.py:23`), so a Messenger without Templates would be reported as `INDETERMINATE` ("platform outcome could not be determined") even though nothing was sent. Today only the hardcoded WhatsApp ref keeps that path unreachable.
- **Deletion test:** Deleting `_messenger` makes complexity vanish: the public `messenger(inbox_ref)` already does the same work. Deleting the `whatsapp_only` call on the Template path also loses nothing once the transport checks the capability itself. `whatsapp_only` stays for `whatsapp_client()` (Media API, limits, validators), where no capability exists.
- **Proposed fix:** `OutboundRuntime.templates(inbox_ref, *, credentials=None)` returns `InboxTemplateTransport(messenger_provider=lambda: runtime.messenger(inbox_ref, credentials=...), inbox_id=inbox_ref.inbox_id)`. In `send`, resolve the Messenger, then call `messenger.capability(ITemplateMessaging)` before any I/O. When it returns `None`, return a `REJECTED` outcome with code `capability_unsupported`, never `INDETERMINATE`. Delete `_messenger`. `InboxExecutionContext.template_transport` passes `self.inbox_ref` and drops `whatsapp_only`. The route maps that rejection to the same 501 that `requires_capability` uses, so the Instagram 501 comes from the capability, not from the Platform name. Net code shrinks; no new abstraction.
- **ADR conflict:** none. This aligns with ADR-0016 ("Hosts check capability(), never the Platform name", line 46) and ADR-0021. The ADR-0006 outcome semantics stay as they are.

### 07-6 Flows have no contract: inbound nfm_reply becomes Unsupported and there is no outbound send (merges 07-6 and 07-7)

- **Files:** `wappa/processors/whatsapp_processor.py`, `wappa/webhooks/whatsapp/message_types/interactive.py`, `wappa/core/messaging/pipeline.py`, `docs/backlog/drafts/261105-mid-whatsapp-flows-prd.md`
- **Principle:** missing-interface
- **Severity:** low (a feature gap that the existing shape can absorb; it does not damage the architecture)
- **Breaking:** no. Public surfaces: the new `IFlowMessaging` capability, and the `MessageType` that Flow replies arrive with (it changes from `UNSUPPORTED`).
- **Evidence:** `KNOWN_INTERACTIVE_REPLY_TYPES` holds only `button_reply`, `list_reply`, `call_permission_reply` (`interactive.py:21-23`). Any other type is rewritten into an Unsupported message, and the comment names Flow replies explicitly (`whatsapp_processor.py:191-206`). `rg nfm wappa/` finds only that comment. No `IFlowMessaging` exists. The draft PRD wants `send_flow` as a WhatsApp-only capability that runs through the pipeline (Scope 1) and a typed inbound reply with `flow_token` from `get_interactive_selection()` (Scope 2) (`261105-mid-whatsapp-flows-prd.md:12-17`). The pipeline today wraps exactly one sending capability: `kind is ITemplateMessaging` in `capability()` (`pipeline.py:267-272`) and `TEMPLATE_METHODS` in `_call_raw` (`pipeline.py:222-227`).
- **Deletion test:** n/a; nothing exists yet.
- **Proposed fix:** Inbound: add `nfm_reply` to `KNOWN_INTERACTIVE_REPLY_TYPES` with a `FlowReply` model (`name`, `body`, `response: dict[str, Any]` decoded from `response_json`, `flow_token`), wired the same way as `call_permission_reply`. `get_interactive_selection()` returns the `flow_token`. Keep the Unsupported fallback with a 200 for genuinely unknown types (ADR-0010). `response` stays a dict because its schema is the Host's Flow definition, not Meta's. Outbound: `IFlowMessaging.send_flow` in `wappa/domain/interfaces/flow_messaging.py`, returned by `WhatsAppMessenger.capability()`. Once Templates and Flows give the pipeline two sending capabilities (a real variation), replace the `TEMPLATE_METHODS` / `kind is` special case with one generic rule: the wrapper puts the owning capability kind on `SendInvocation`, and `_call_raw` calls `self._raw.require_capability(invocation.capability)`. Do not build that rule before `IFlowMessaging` exists. Data-exchange crypto and Flow management stay out of the Messenger (PRD phase 2).
- **ADR conflict:** none. ADR-0016 rule 4 places it behind a capability.

## Rejected findings

- **07-1 MessengerPipeline hardcodes Templates.** The code is real (`pipeline.py:222-227`, `267-272`, `_PipelineTemplates` at `603-700`; the auditor's `template_messaging.py:57-59` citation is actually lines 77-79). But there is only one sending capability today, so a registry or marker base would be a hypothetical seam. The auditor's own fix says not to build it yet. Adding Flows costs one `kind is` line and one wrapper class, which is needed anyway because each wrapper declares a different signature. Its trigger is recorded under 07-6.
- **07-3 Collapse the three Template methods and requests into one send_template.** The ADR-0016 contract map lists "text / media / location Templates" (`0016-one-messenger-method-per-action.md:35`); rule 1 (line 9) concerns one action across Platforms, not merging three header kinds on one Platform. The variants differ in validation (`reject_authentication_header` on media and location, `template_transport.py:280-298`) and in middleware method names that window guards key on (`pipeline.py:603-608`). Collapsing would break Hosts, routes and middleware for little gain. The repeated `DirectMessage(...)` construction in `_send_request` (`template_transport.py:580-622`) is three lines of cosmetic duplication.
- **07-5 InboxTemplateTransport reaches into OutboundRuntime private API.** This is a duplicate of 07-4 and is merged there. Keeping `TemplateEndpoint` in the transport is correct, because it encodes ADR-0006 routing semantics.
- **07-7 Flows outbound is unbuilt.** This is a duplicate of 07-6 (the same missing Flows contract) and is merged there.
- **07-8 Calls: CallWebhook Platform-specific, SSE identity branch in shared runtime.** `CallWebhook` and `process_call` are legitimate under ADR-0016 rule 4 (line 17), which the auditor concedes. The leaky part, `_derive_sse_identity` testing `PlatformType.WHATSAPP` and isinstance over `InboundMessageWebhook`, `CallWebhook`, `StatusWebhook` and `ErrorWebhook` (`wappa/core/inbound/runtime.py:388-410`), is not Calls-specific. It is a general inbound-runtime and SSE concern, so it belongs to that area's audit. Fixing it only for Calls would split one rule in two. `ICallControls` is backlog (`261105-mid-whatsapp-calling-prd.md:12-21`), not a defect, so it appears in the interface proposal.
- **07-9 capability() if-chain and WhatsAppMessenger subclassing ITemplateMessaging.** The auditor's deletion test concludes "fine at two entries, not worth changing". Removing `ITemplateMessaging` from the MRO (`whatsapp_messenger.py:57`) would mean extracting the messenger's `_deliver` / recipient-ordering logic that the Template methods use (`whatsapp_messenger.py:740-772`), which is more code with no behaviour gain. Through the pipeline, Hosts already get `_PipelineTemplates`, not the raw messenger (`pipeline.py:267-272`).

## Checked and legitimate

- `IMessenger.capability()` / `require_capability()` (`wappa/domain/interfaces/messaging_interface.py:51-66`): the single discovery seam for Platform-only features. A missing capability raises `UnsupportedOperationError`.
- `ITemplateMessaging` is a separate interface (`wappa/domain/interfaces/template_messaging.py:28-74`); `IMessenger` carries no Template methods.
- `WhatsAppMessenger.capability()` (`wappa/messaging/whatsapp/messenger/whatsapp_messenger.py:80-86`): a two-entry `kind is` chain inside the WhatsApp adapter, which is the right home for it.
- `pipeline.py:267-272`: non-message capabilities (`IMediaLibrary`, `ICommentControls`) deliberately bypass message middleware; Templates are wrapped so window guards still see them.
- The `TemplateTransportOutcome` four-outcome model and `resolve_template_route` (`template_transport.py:635-652`) encode the ADR-0006 non-retry safety semantics a Host depends on. They are not over-engineering.
- `CallWebhook` and `EventHandler.process_call`: a single-Platform event family with its own Universal Webhook type, per ADR-0016 rule 4.
- `whatsapp_processor.py:191-206`: Unsupported with a 200 for unknown interactive types is the right safety net (ADR-0010); only `nfm_reply` should be promoted out of it.
- `whatsapp_only` for `whatsapp_client()` (`inbox_context.py:163-177`), covering the Media API, limits and validators: no capability exists and no second Platform needs one, so an explicit 501 gate is acceptable there.
- `MessengerFactory` checking the Platform (`wappa/domain/factories/messenger_factory.py:111`): a composition root, the right home for a Platform branch.

## Interface proposal

`IMessenger.capability(kind)` stays the only discovery path. Instagram returns `None` for every capability below, so `require_capability` raises `UnsupportedOperationError` and routes answer 501 through `requires_capability`. No neutral interface is added for Templates, Flows or Calls, because each has one adapter.

- `ITemplateMessaging` (exists, unchanged): `send_text_template`, `send_media_template`, `send_location_template`. It is reached in Host code through `OutboundRuntime.templates(inbox_ref)` → `InboxTemplateTransport.send(request) -> TemplateTransportResult`, which checks the capability before any I/O and reports `REJECTED` (never `INDETERMINATE`) when it is missing. `OutboundRuntime` moves to `wappa/messaging/outbound_runtime.py`.
- `IFlowMessaging` (new, when the Flows PRD is taken up): `send_flow(target: DirectMessage, flow: FlowRef, body: str, cta: str, *, header=None, footer=None, screen=None, data=None) -> MessageResult`. `FlowRef` holds the id or name, the mode (draft or published), the action (navigate or data_exchange) and the `flow_token`. It is a sending capability, so it runs through message middleware. Once it lands, `SendInvocation` carries its owning capability kind and `_call_raw` replaces `TEMPLATE_METHODS` with `require_capability(invocation.capability)`. Template-launched Flows stay a Template button concern on `ITemplateMessaging`. Inbound Flow replies become a typed `nfm_reply` interactive message (`FlowReply`), with `flow_token` returned by `get_interactive_selection()`.
- `ICallControls` (new, when the Calling PRD is taken up): `pre_accept(call_id, sdp_answer)`, `accept(call_id, sdp_answer)`, `reject(call_id)`, `terminate(call_id)`, `start_call(target, sdp_offer)`, `request_call_permission(target, body)`. Each is one action returning `OperationOutcome`. It does not send a conversation message, so it bypasses message middleware like `IMediaLibrary`. Inbound stays `CallWebhook` + `process_call`.
- Calling settings and Flow management go behind separate admin capabilities, never on the Messenger (ADR-0016 rule 6).
