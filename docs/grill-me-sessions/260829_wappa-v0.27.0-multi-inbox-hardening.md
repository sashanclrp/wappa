# Grilling Session — Wappa v0.27.0 Multi-Inbox Hardening

This session resolves the architecture before the v0.27.0 backlog series is
rewritten. It covers four connected seams: the Inbox directory, payload-routed
WhatsApp ingress, Inbox-scoped HTTP operations, and PostgreSQL session access.

The questions are grouped in dependency order. Answering a later question may
depend on an earlier answer. Each question includes a recommendation grounded in
the current code, not only in the proposed design.

## What the code does today

- `IInboxCredentialStore` is open-ended. A Host Application can implement its
  methods however it wants.
- `DatabaseInboxCredentialStore` reads a host-owned `wappa_inboxes` SQL table,
  caches individual credentials in raw Redis hashes, and queries PostgreSQL
  directly for every WABA reverse lookup.
- Wappa already has `ITableCache` and `TypedTableCache[T]`, but those tables are
  scoped by an Inbox. The Inbox directory cannot use an Inbox-scoped namespace
  to discover the Inbox in the first place.
- `ITableCache.find_by_field()` is not part of the interface and the Redis
  implementation returns only the first match. It cannot satisfy the required
  one-WABA-to-many-Inboxes lookup.
- `InboxMiddleware` currently applies `X-Wappa-Inbox-ID` to every non-public
  `/api/whatsapp/*` request, including static limits and local validation routes
  that do not use Meta or Inbox-scoped state.
- `self.db` opens a primary PostgreSQL session. It supports reads and writes.
  `self.db_read` chooses a healthy startup-time read replica in round-robin
  order, or falls back to the primary when no replica is available. The caller,
  not SQL inspection, chooses which factory to use.

## Decisions already agreed

These are recorded as inputs, not questions to reopen accidentally.

1. Wappa owns the canonical Pydantic shape of an Inbox credential record and
   the behavior of multi-Inbox resolution. Explicit-mode applications supply
   records and infrastructure conforming to that contract; they do not invent
   their own record shape or routing semantics.
2. The hot webhook path must not query PostgreSQL for every delivery. Explicit
   mode uses a Wappa-defined Redis-backed directory contract with read-through
   loading on a miss.
3. Platform Account lookup follows the same rule. Its identity, record shape,
   filtering, ordering, and cache behavior belong to Wappa. The settled
   internal contract is
   `list_inbox_refs_for_platform_account(account_ref)`.
4. Meta POST callbacks must be authenticated with
   `X-Hub-Signature-256 = HMAC-SHA256(app_secret, raw_body)` before Wappa parses
   or routes the payload. `WP_WEBHOOK_VERIFY_TOKEN` remains exclusive to the GET
   challenge handshake.
5. Legacy single-Inbox settings and explicit multi-Inbox operation must coexist.
   Explicit mode cannot silently fall back to `WP_PHONE_ID`.
6. The Inbox Directory is application-scoped, not Inbox-scoped. It reuses the
   existing `ITableCache` under Wappa's reserved `SYSTEM_SCOPE = "__system__"`.
   `InboxDirectoryTable` is a ready-to-use concrete Wappa module over that
   cache, not a second cache interface or Redis adapter.
7. Cached Inbox records and their reverse-index keys have a 60-minute sliding
   TTL. Every successful hit renews the relevant TTLs. A key disappears only
   after 60 minutes with no lookup.
8. Each Host Application owns its durable database schema. It supplies the
   adapter that maps a database result into Wappa's Pydantic record. On the
   first cache miss, Wappa calls that adapter and stores the validated record in
   the Inbox Directory through its cache infrastructure, normally Redis.
9. Symphonai uses the same Table Cache mechanism at three scopes: System for
   application-wide runtime data, Owner for facts shared by an Owner's Inboxes,
   and Inbox for Platform-facing conversation state. Wappa interprets System
   and Inbox. Owner remains a Symphonai concept carried as a host-defined Table
   Cache scope.
10. `context_id` replaces `inbox_id` only in the Table Cache construction API.
    This is a DDD language correction, not a behavior or key-format change.
    User, State, AI State, Expiry, PubSub, and other Wappa runtime caches remain
    Inbox-scoped and keep `inbox_id`.
11. `InboxDirectoryTable` is mandatory and Wappa-owned. Explicit-mode Host
    Applications cannot replace it with their own table, credential store,
    cache layout, reverse lookup, TTL policy, or routing rules. They adapt their
    durable schema through `IInboxDirectorySource`; Wappa constructs and runs
    the directory.
12. `WP_ACCESS_TOKEN` remains an optional legacy single-Inbox WhatsApp input in
    v0.27.0. Explicit multi-Inbox mode rejects `WP_ACCESS_TOKEN`, `WP_PHONE_ID`,
    or `WP_BID` at startup rather than ignoring an ambiguous second credential
    source. Do not rename it to `META_ACCESS_TOKEN`; Wappa does not define one
    process-wide credential valid for every Meta Platform.
13. `inbox_id` is unique within a Platform. Wappa's globally unique runtime
    identity is `InboxRef(platform, inbox_id)`. Cross-Platform routing,
    persistence, caches, and events must not compare or namespace an Inbox by
    raw `inbox_id` alone.
14. Explicit multi-Inbox mode requires `SYSTEM_TOKEN_ENC_KEY`. Wappa owns the
    encryption and decryption of every Inbox credential secret. Host
    Applications must call Wappa to create the encrypted credential envelope
    they persist, return that envelope through `IInboxDirectorySource`, and
    never decrypt it themselves. The setting does not encrypt unrelated Host
    Application data.
15. A Platform Account ID is unique only inside its Platform. Wappa represents
    the global identity as `PlatformAccountRef(platform, platform_account_id)`.
    Account lookup returns `InboxRef` values, not unqualified Inbox IDs.
16. The WABA reverse index is a Wappa-owned typed Table Cache row under
    `SYSTEM_SCOPE`. It is not a raw Redis Set and does not introduce a
    Redis-only directory contract.
17. A phone-scoped WhatsApp change must prove that its active Inbox record
    belongs to `entry[].id`. A mismatch rejects the complete batch with `400`.
18. A successful source lookup with no active members creates a fixed-TTL
    empty index and rejects the payload with `400`. An indeterminate lookup or
    failed repair returns `503` and does not cache an empty result.
19. One Wappa application binds to exactly one Meta App configuration. That
    application may handle many WABAs and Inboxes under the Meta App, but Wappa
    does not select among several Meta App Secrets inside one application.
20. Wappa owns one immutable `MetaApplicationConfig`. The Host Application
    supplies it explicitly or lets Wappa build it from environment settings;
    configuring both sources is a startup error. Inbox routing mode does not
    change this application-level configuration.
21. WhatsApp POST authentication uses `META_APP_SECRET`, never
    `WP_WEBHOOK_VERIFY_TOKEN`. Missing, malformed, or mismatched
    `X-Hub-Signature-256` returns the same generic `401` before JSON decoding or
    Inbox lookup.
22. Wappa has no development bypass for WhatsApp POST authentication. Mounting
    the callback requires the Meta App Secret and webhook verify token at
    startup in every environment.
23. Symphonai chooses Wappa's environment-backed Meta configuration path. It
    declares `META_APP_SECRET` once in the shared process environment. Wappa
    reads that value directly, so the Wappa integration does not add a second
    setting or pass a `MetaApplicationConfig` object.
24. `X-Wappa-Inbox-ID` selects runtime scope and never authorizes a caller.
    Only routes that touch Meta or Inbox-scoped Wappa state resolve an
    `InboxExecutionContext`; local validation and static-limit routes ignore
    the header.
25. Inbox routing has two explicit modes, `legacy` and `explicit`. The removed
    `auto` mode cannot hide competing credential authorities. An omitted mode
    defaults to `legacy` for existing single-Inbox consumers.
26. `db` remains the primary session factory and `db_read` remains the
    read-intent session factory. They stay optional and do not promise database
    row isolation by Inbox. Replica reads provide eventual consistency.
27. The intended hardened `db_read` contract uses read-only transactions,
    read-specific teardown, observable fallback, replica rotation before query
    execution, and cooldown. That implementation belongs to a separate
    PostgreSQL plugin PRD rather than the v0.27 release blockers.
28. WhatsApp intake uses stable `400`, `401`, `404`, and `503` mappings and
    finishes authentication, routing, membership validation, and every Dispatch
    Context before scheduling any delivery.
29. Wappa does not deduplicate webhook deliveries or invent a generic delivery
    fingerprint in v0.27. Delivery identity needs its own later design because
    a batch position or payload hash can collapse legitimate events.
30. `InboxDirectoryTable` depends on `ITableCache`, not a directory-specific
    Redis adapter. Domain models and ports, directory orchestration, Table Cache
    persistence, credential crypto, Platform mapping, and HTTP adaptation keep
    separate module ownership.
31. The v0.27 release is blocked on the multi-Inbox identity, credential,
    authentication, routing, membership, failure, test, and documentation
    contracts recorded in 10d. PostgreSQL replica hardening and delivery
    identity remain separate PRDs.
32. Encryption-secret rotation is a v0.27 release blocker. Wappa reads one
    active `SYSTEM_TOKEN_ENC_KEY` plus optional
    `SYSTEM_TOKEN_ENC_PREVIOUS_KEYS`, decrypts through `MultiFernet`, and exposes
    a re-encryption command that never returns plaintext to the Host
    Application.

## 1. The public abstraction: Store, Directory, or Table

### 1a. What does an explicit-mode Host Application inject?

Should it inject an arbitrary `IInboxCredentialStore`, a concrete
`TypedTableCache[InboxCredentialRecord]`, or a Wappa-owned directory assembled
from smaller ports?

**My recommendation:** Make `InboxDirectory` the Wappa module used by the
runtime. Wappa obtains an `ITableCache` bound to `SYSTEM_SCOPE` and constructs
`InboxDirectoryTable` with its own Pydantic model. The host supplies only the
persistent source adapter. Wappa implements credential lookup, active checks,
WABA reverse lookup, ordering, cache keys, and invalidation. Do not let the
runtime depend directly on host-written routing rules.

`IInboxCredentialStore` can remain the small read port consumed by Messenger
and Inbound Runtime, but explicit application assembly should produce the
Wappa-owned implementation rather than inviting arbitrary implementations.

**Answer:** Agreed. There is no `IInboxDirectoryTable`. Explicit mode provides
the Host Application's persistent source adapter and configured cache
infrastructure. Wappa builds a system-scoped `ITableCache`, wraps it in the
concrete `InboxDirectoryTable`, and exposes the smaller
`IInboxCredentialStore` read behavior to Messenger and Inbound Runtime.

### 1b. Can the Inbox Directory reuse `ITableCache`?

The existing Redis Table Cache already puts its constructor scope in the first
key segment. Symphonai proves that an application-wide table works by passing
`SYSTEM_SCOPE = "__system__"`; its current helper exists because Wappa does not
provide that construction directly.

**My recommendation:** Yes. Keep one `ITableCache` contract and the existing
Redis implementation. Wappa should export the reserved `SYSTEM_SCOPE` and a
builder such as `build_system_table_cache()` so consumers never construct a
fake `ICacheFactory` context themselves. `InboxDirectoryTable` then uses that
table and owns only Inbox-directory behavior.

**Answer:** Agreed. Reuse `ITableCache` under the exact reserved scope
`__system__`. Do not create `IInboxDirectoryTable`, `ITableGlobalCache`, or a
second Redis adapter. Wappa provides `InboxDirectoryTable` ready to use, and
Symphonai can replace its local system-table construction with the Wappa
builder.

### 1c. Who is allowed to mutate the Redis directory?

If hosts write raw Redis rows themselves, Wappa cannot guarantee Pydantic
validation, secondary indexes, credential revisioning, or atomic deactivation.

**My recommendation:** Do not accept a caller-supplied credential record on the
mutation command. After its business transaction commits, the host calls a
Wappa-owned command such as `refresh_inbox(inbox_ref)`. Wappa reloads that Inbox
through `IInboxDirectorySource`, validates the canonical Pydantic record, and
projects the result into the primary cache row and reverse index. The same
command handles onboarding, credential rotation, activation, deactivation, and
durable deletion according to the state returned by the source.

This gives Wappa one database-to-directory mapping path. A host cannot commit
one value and then accidentally push a different value into Redis. It also
keeps the Host Application out of Wappa's cache schema.

**Answer:** Agreed. Only Wappa mutates the Redis Inbox Directory. The Host
Application mutates its durable database, commits, and then calls the
source-driven `refresh_inbox(inbox_ref)` command. It never supplies a raw cache
row or a caller-built canonical record to a mutation command.

1. The public command is source-driven `refresh_inbox(inbox_ref)`, not
   record-driven `upsert_inbox(record)`.
2. The host calls it only after its durable transaction commits. The command is
   idempotent and raises on source or cache failure so the host can retry.
3. The durable source supplies a `credential_version` that increases across
   the full lifetime of an `inbox_id`, including deactivation and recreation.
   Wappa accepts a higher version. An equal version is idempotent only when the
   canonical record is identical; conflicting data at the same version raises
   an integrity error. Retrying an identical version still repairs its derived
   index membership and completes Messenger eviction. An older refresh cannot
   replace newer cached credentials.
4. An inactive or durably absent Inbox produces a short-lived negative record,
   removes that Inbox from Platform Account indexes, and evicts its cached
   Messenger. Wappa does not expose immediate hard deletion as a normal host
   command.
5. Wappa orders multi-row writes for safe partial failure and supplies repair.
   It writes the inactive or active primary row before changing reverse
   indexes. Webhook fan-out still validates every routed Inbox, so a stale index
   cannot reactivate an inactive Inbox. Retrying `refresh_inbox(inbox_ref)`
   repairs a missed index update; an optional bulk reconciler can call the same
   command rather than owning another write path.

`credential_version` is mandatory in the canonical record. Active records use
the agreed 60-minute sliding TTL. Inactive and absent records use a fixed
60-minute TTL; hits do not renew a negative record forever.

### 1d. Is `IInboxCredentialStore` still a public extension point?

There are useful test and specialized deployment cases for an in-memory store,
but an unrestricted production extension point weakens the contract agreed
above.

**My recommendation:** Keep the read interface as Wappa's internal dependency
inversion boundary and as a test seam, but do not accept consumer-written
production implementations. The only production paths are:

- `SettingsInboxCredentialStore` for legacy single-Inbox operation.
- Wappa's `InboxDirectoryTable` for explicit multi-Inbox operation.

Explicit assembly accepts `IInboxDirectorySource`, not
`IInboxCredentialStore`. Wappa constructs the directory and its read port. This
prevents a Host Application from changing active-Inbox rules, WABA fan-out,
cache renewal, error semantics, or credential invalidation behind an object
that happens to have the same method names.

**Answer:** Agreed. Host Applications may not create or inject their own
`InboxDirectoryTable` or production `IInboxCredentialStore`. Their mandatory
adaptation point is `IInboxDirectorySource`, which maps their durable data into
Wappa's canonical records. Wappa owns everything after that boundary.

Why retain an internal port at all? Wappa still has two production credential
resolution policies: the legacy settings-backed single-Inbox adapter and the
Wappa-owned multi-Inbox directory. Messenger, inbound routing, middleware, and
other callers should not branch on that boot mode. They need one narrow
capability that can resolve an Inbox and answer Platform Account membership.
The port keeps that mode selection at assembly time. Tests also gain a cheap
fake, but test convenience alone would not justify the abstraction.

The current `IInboxCredentialStore` shape needs another pass. Its
`get_credentials()`, `validate_inbox()`, and Platform Account lookup are read
operations. `invalidate_cache()` is a directory command, while
`default_inbox_id` is legacy routing policy. Keeping all five members on one
interface weakens interface segregation and lets directory mechanics leak into
runtime consumers.

**My recommendation:** Retain the internal dependency-inversion boundary, but
rename or split it around the capability the runtime consumes. A candidate is
`IInboxCredentialResolver` for credential and routing reads. Put proactive
cache invalidation on the concrete Wappa-owned directory command API, and keep
legacy default-Inbox selection in assembly or a routing-policy object. Do not
export the internal resolver as a Host Application extension point.

**Answer:** Agreed. Rename the internal read port to
`IInboxCredentialResolver` and remove it as a Host Application extension
point. `SettingsInboxCredentialResolver` and Wappa's `InboxDirectoryTable`
implement it. Directory mutation stays on the Wappa-owned directory command
API, while legacy default-Inbox selection belongs to application assembly or a
routing-policy object.

### 1e. What persistent source contract does each Host Application implement?

The host may use SQLModel, raw SQLAlchemy, another ORM, or a different database.
Wappa still needs the same two reads.

**My recommendation:** Define a Wappa-owned `IInboxDirectorySource` with these
semantic operations:

```python
async def get_inbox(inbox_id: str) -> InboxCredentialRecord | None: ...

async def list_inboxes_for_platform_account(
    platform: PlatformType,
    platform_account_id: str,
) -> tuple[InboxCredentialRecord, ...]: ...
```

The host implements the queries and maps its rows to Wappa records. Wappa
validates the returned values, filters active records according to the agreed
contract, writes the cache, and builds the reverse index. Do not expose a
generic callback that returns arbitrary dictionaries.

**Answer:** Direction agreed. Wappa defines the returned Pydantic shape and the
cache-population sequence; each app defines the persistent query. The exact
method names and whether inactive records may be returned remain open.

### 1f. Must the system-scoped `ITableCache` always use Redis?

**My recommendation:** Keep the port backend-neutral, but ship Redis as the
built-in production adapter. Memory is useful for tests and a single-process
development app. A production multi-worker adapter must provide shared state,
sliding TTL renewal, and atomic record/index updates; an arbitrary local cache
does not meet that contract.

**Answer:** The interface remains backend-neutral. Wappa's ready production
path uses the existing Redis `ITableCache` and its existing table pool. Memory
may support tests or single-process development if it passes the same behavior
tests.

### 1g. Are System, Owner, and Inbox cache scopes hierarchical?

Calling them three levels can imply that an Inbox read falls back to Owner and
then System, or that invalidating an Owner automatically clears every Inbox.
Neither behavior follows from the current cache implementation.

**My recommendation:** Treat them as three sibling namespaces selected by data
ownership. There is no implicit lookup fallback, inheritance, or cascading
invalidation. A Symphonai service may combine values from several scopes, but
the service owns that composition.

For one person contacting the same Owner through Instagram and WhatsApp, Wappa
keeps two Inbox-scoped User contexts. Symphonai may link them to one Owner-level
identity, profile, or configuration, but that link must not merge their Wappa
conversation state.

**Answer:** Agreed on the three scopes. System data applies across the app;
Owner data may span several Inboxes; Inbox data remains separate per Platform
Inbox. Automatic fallback and cascading invalidation are not part of the
contract.

### 1h. What values bind the three Table Cache contexts?

`ITableCache` accepts one opaque `context_id` for its existing first key
segment. Wappa does not inspect whether a host-defined value represents an
Owner, workspace, portfolio, or another business concept.

**My recommendation:** Keep the existing values and existing Redis key shapes:

```text
System context: context_id = "__system__"
Owner context:  context_id = str(owner_id)  # Symphonai only
Inbox context:  context_id = InboxRef.cache_namespace
```

Wappa reserves `__system__`; no real Inbox or host-defined context may use it.
The Host Application must keep its other Table Cache context IDs distinct
inside one Redis Table Cache database.

**Answer:** Revised by question 2c. System and Owner values remain unchanged.
An Inbox-owned Table Cache uses the namespace derived from
`InboxRef(platform, inbox_id)`. Wappa preserves the existing raw WhatsApp
namespace for compatibility and qualifies every future Platform namespace.
This collision-protection rule is separate from the `context_id` parameter
rename, which still causes no cache migration by itself.

### 1i. Does `context_id` replace `inbox_id` across every cache contract?

**My recommendation:** No. Rename only the optional parameter used to construct
an `ITableCache`:

```python
cache_factory.create_table_cache(context_id=...)
```

When omitted, `context_id` defaults to the namespace derived from the factory's
active Inbox Reference. Normal handler code does not construct that namespace.
Positional callers keep working. A caller that explicitly uses the old keyword
gets a Python `TypeError` and fixes it by replacing `inbox_id=` with
`context_id=`. Wappa provides no alias because v0.27.0 is a clean contract
break.

`UserCache`, `StateCache`, `AIStateCache`, `ExpiryCache`, PubSub, SSE, and every
other runtime cache keep `inbox_id`. Their records are owned by an Inbox. Table
Cache alone can hold arbitrary Pydantic records and DB-derived read models at a
System, host-defined, or Inbox context.

The rename applies to the shared Table Cache construction contract and every
backend implementing it. Restricting the name change to Redis would make
`ITableCache` mean something different under memory and JSON adapters.

**Answer:** Agreed. This is a Table Cache naming change only. It must not alter
cache behavior, backend selection, key generation, TTL handling, serialization,
or existing cached data.

## 2. Canonical Inbox credential record

### 2a. Is this the v1 Pydantic record?

The original candidate used one model with `is_active: bool = True`. That shape
can activate a record when a host forgets the field, and an inactive record
still has to carry the old access token.

**My recommendation:** Make activity an explicit discriminator and require a
token only on the active member:

```python
class WhatsAppActiveInboxCredentialRecord(BaseModel):
    schema_version: Literal[1] = 1
    inbox_id: NonEmptyStrictStr
    platform: Literal[PlatformType.WHATSAPP] = PlatformType.WHATSAPP
    platform_account_id: NonEmptyStrictStr
    status: Literal[InboxCredentialStatus.ACTIVE]
    access_token: EncryptedSecretEnvelope
    credential_version: PositiveInt
    updated_at: AwareDatetime


class WhatsAppInactiveInboxCredentialRecord(BaseModel):
    schema_version: Literal[1] = 1
    inbox_id: NonEmptyStrictStr
    platform: Literal[PlatformType.WHATSAPP] = PlatformType.WHATSAPP
    platform_account_id: NonEmptyStrictStr
    status: Literal[InboxCredentialStatus.INACTIVE]
    credential_version: PositiveInt
    updated_at: AwareDatetime
```

`IInboxDirectorySource.get_inbox()` returns the active or inactive member, or
`None` when the Inbox has never been registered. Wappa may cache that confirmed
absence as its own fixed-TTL miss marker; the miss marker is not an Inbox
Credential Record and never contains a token.

Require `platform_account_id` for WhatsApp. Payload routing cannot validate
WABA membership or fan out account-scoped events without it.

**Answer:** Agreed. Wappa owns the model and uses the active/inactive
discriminated union above. The six constraints below are mandatory:

1. Use the active/inactive discriminated union above instead of a defaulted
   `is_active` boolean.
2. Treat `inbox_id` as unique within one Platform. WhatsApp continues to use
   Meta's `phone_number_id` exactly. Wappa uses
   `InboxRef(platform, inbox_id)` as the globally unique runtime identity.
3. Require each active Inbox snapshot to contain its access token, even when
   several Inboxes share the same Meta token.
4. Keep Meta App Secret, webhook verify token, Graph API version, and base URL
   out of the Inbox record. They belong to application-level Meta
   configuration selected before webhook parsing.
5. Require non-empty strict identifiers, `credential_version >= 1`, and a
   timezone-aware `updated_at`. The timestamp supports operations but never
   decides write ordering.
6. Persist a Wappa `EncryptedSecretEnvelope` in the canonical stored record.
   Wappa accepts the plaintext as `SecretStr` only at credential creation or
   rotation, encrypts it before returning a persistable record, and decrypts it
   only into internal Resolved Inbox Credentials. The generic Table Cache must
   never receive plaintext `SecretStr`; its current serializer would turn that
   value into `**********`.

### 2b. One generic record or a Platform-discriminated union?

A generic `access_token` happens to work for WhatsApp today but may not model
another Platform's credential bundle.

**My recommendation:** Define `InboxCredentialRecord` as a discriminated union
of Platform-specific Pydantic records. Ship only
`WhatsAppInboxCredentialRecord` in v0.27.0. Keep `inbox_id`, `platform`,
`platform_account_id`, `status`, `credential_version`, and `updated_at` as
shared fields; each Platform member defines its own credential fields.

`WP_ACCESS_TOKEN` is a legacy environment input used to build one WhatsApp
record. It is not the canonical field name and does not prove that the physical
token is WhatsApp-only. A Meta system-user token can carry permissions for
several assigned assets, so a host may map the same physical token into several
Inbox records. Other Meta APIs also use token types such as User, Page, or
Instagram User tokens. Wappa must therefore model the credential required by
each Platform operation instead of assuming one application-wide Meta token.

Meta documents both user and system-user tokens for WhatsApp Cloud API. Its
Instagram API documentation describes User, Page, and Instagram User access
tokens. One physical token may authorize several WhatsApp phone numbers or
other Graph API operations when its app, permissions, principal, and assigned
assets allow it. That does not make the token valid for every Meta product.

- [Meta WhatsApp Cloud API documentation](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api)
- [Meta Instagram API documentation](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api)

The Platform-discriminated union permits different credential shapes without
requiring different physical token values:

```python
InboxCredentialRecord = Annotated[
    WhatsAppInboxCredentialRecord
    | InstagramInboxCredentialRecord
    | TelegramInboxCredentialRecord,
    Field(discriminator="platform"),
]

WhatsAppActiveInboxCredentialRecord(
    platform="whatsapp",
    access_token=token,
    ...,
)

# A future adapter chooses the credential its supported Instagram API needs.
InstagramActiveInboxCredentialRecord(
    platform="instagram",
    page_access_token=token,
    ...,
)

# Another supported Instagram API might require this shape instead.
InstagramActiveInboxCredentialRecord(
    platform="instagram",
    instagram_user_access_token=token,
    ...,
)
```

The WhatsApp and Instagram records may contain the same physical token. The
union only requires each Platform member to name and validate the credential
its adapter consumes.

There are three distinct naming levels:

| Level | Name | Meaning |
|---|---|---|
| Legacy environment input | `WP_ACCESS_TOKEN` | Supplies the single-Inbox WhatsApp compatibility mode. |
| WhatsApp record field | `access_token` | Bearer token used by the WhatsApp adapter for one Inbox. |
| Possible future shared model | `MetaSystemUserCredential` | A concrete credential kind that several Platform records might reference. It does not exist in v0.27.0. |

Do not rename the legacy variable to `META_ACCESS_TOKEN` in v0.27.0. That name
would imply one process-wide token shared by every Meta Platform, which Wappa
does not guarantee. If Wappa later introduces a Meta credential aggregate, it
should name the concrete token kind, such as a Meta system-user token, and let
WhatsApp and Instagram records refer to it only when both adapters support that
contract.

**Direct decision:** Yes, `WP_ACCESS_TOKEN` still makes sense as an optional
environment variable for legacy single-Inbox WhatsApp operation. Yes, keep that
name in v0.27.0. `WP_` names the Wappa adapter consuming the credential, not the
Meta system that issued the physical token. Explicit multi-Inbox mode rejects
`WP_ACCESS_TOKEN`, `WP_PHONE_ID`, and `WP_BID` at startup. Every active Inbox
record comes from `IInboxDirectorySource`, so accepting a second credential
source would weaken the mode boundary.

If Wappa later replaces the abbreviation, `WHATSAPP_ACCESS_TOKEN` is more exact
than `META_ACCESS_TOKEN`. Such a rename should use a deprecation window and is
outside this feature.

**Answer:** Direction agreed. One application-scoped table holds records for
every supported Platform, and the Platform discriminator chooses the Pydantic
member. v0.27.0 ships only the WhatsApp member. Keep `WP_ACCESS_TOKEN` as the
optional legacy single-Inbox input; explicit multi-Inbox mode rejects the
legacy Inbox environment bundle and resolves each record through the mandatory
directory source. Instagram credentials and a possible shared Meta credential
aggregate remain outside this feature.

### 2c. Is `inbox_id` globally unique or unique only within a Platform?

The current runtime and cache keys treat `inbox_id` as globally unique. A
future Telegram identifier could collide with a Meta phone number ID.

**My recommendation:** Keep each Platform's native identifier as `inbox_id` and
introduce the immutable value object `InboxRef(platform, inbox_id)`. Equality,
directory rows, Messenger caches, event scopes, and every Inbox-owned cache use
the composite reference. Platform-specific HTTP routes already know their
Platform; internal calls carry the value object rather than passing two loose
strings.

Preserve today's WhatsApp cache namespace because Meta phone number IDs are
validated as numeric. Future Platforms use a qualified namespace such as
`telegram:<native-id>`. This avoids invalidating existing WhatsApp state while
preventing a future Telegram or Instagram identifier from colliding with it.
Wappa owns namespace encoding; Host Applications do not concatenate it.

**Answer:** Agreed. `inbox_id` is unique within a Platform. The globally unique
Wappa runtime identity is `InboxRef(platform, inbox_id)`. For WhatsApp,
`inbox_id` remains Meta's exact `phone_number_id`. This decision protects the
unlikely cross-Platform collision and requires Platform qualification anywhere
Wappa stores, compares, or routes Inboxes outside a Platform-specific boundary.

### 2d. May several Inboxes share one access token?

Meta system-user tokens commonly span several phone numbers. Copying the token
into each row makes Inbox resolution atomic and simple, but duplicates secrets.

**My recommendation:** Allow duplicate token values in v1. Each Inbox record is
a complete runtime credential snapshot, so one Redis read is enough. Do not
introduce a second secret-reference aggregate until there is a concrete
rotation or storage requirement that justifies the extra lookup and failure
mode.

**Answer:** Agreed. Every active Wappa Inbox record contains the usable
access-token `EncryptedSecretEnvelope`, even when several records protect the
same physical Meta token. The Host Application may normalize that envelope in
its durable schema. Its `IInboxDirectorySource` must return a complete active
stored record without decrypting the envelope. Wappa resolves the usable token
internally.

So yeah, totally agree. Trying to de-duplicate brings more complexity, and solve no-problem.

### 2e. What is Wappa's secret-at-rest boundary?

`SecretStr` prevents accidental representation in logs; it does not encrypt a
Redis value.

An access token must never be hashed for storage. Wappa must recover the exact
token to place it in Meta's bearer authorization header, and a cryptographic
hash is intentionally irreversible. Valid storage options are reversible
encryption or an external secret manager. For Wappa's explicit Inbox
Credential Record contract, the accepted representation is the Wappa-created
`EncryptedSecretEnvelope`; plaintext is never a valid durable or cache value.

**My recommendation:** Make Wappa encryption mandatory for every durably stored
Inbox credential in explicit multi-Inbox mode. Wappa owns one concrete
credential-protection service rather than exposing an arbitrary host-written
`SecretCodec`. Use the high-level authenticated Fernet recipe from
`cryptography`; `SYSTEM_TOKEN_ENC_KEY` contains the URL-safe base64-encoded
32-byte Fernet secret generated by `Fernet.generate_key()`.
The official recipe documents authenticated tokens and `MultiFernet` rotation:
[cryptography Fernet documentation](https://cryptography.io/en/stable/fernet/).

Wappa encrypts a context-bound envelope, not the token string alone. The
plaintext envelope includes its format version, Platform, `inbox_id`, secret
field name, and token value. After decryption, Wappa verifies that metadata
against the cache row before returning `SecretStr`. Moving ciphertext between
Inbox rows therefore fails validation even though both rows use the same
encryption secret.

`SYSTEM_TOKEN_ENC_KEY` is required when Wappa creates or consumes explicit-mode
Inbox Credential Records. Missing or malformed configuration fails startup.
Legacy single-Inbox mode reads `WP_ACCESS_TOKEN` from process configuration and
does not create a durable encrypted record.

The boundary is strict:

- The Host Application passes a plaintext `SecretStr` to a Wappa credential
  creation or rotation method. Wappa returns a canonical record containing an
  `EncryptedSecretEnvelope`; only that record may be persisted.
- `IInboxDirectorySource` returns the stored encrypted record. It does not
  decrypt secrets or return plaintext `SecretStr`.
- `InboxDirectoryTable` validates and caches the same encrypted record. Wappa's
  internal resolver decrypts only when a Platform adapter needs Resolved Inbox
  Credentials.
- Wappa never emits plaintext secrets in logs, exceptions, health output,
  events, cache inspection helpers, or model representations.
- The Host Application chooses its database schema and writes the canonical
  encrypted envelope after its business validation. It never implements the
  cipher or sees decrypted values on reads.
- The Host deployment still supplies TLS, database and Redis authentication,
  access controls, and network isolation. Credential encryption does not
  replace those controls.
- `SYSTEM_TOKEN_ENC_KEY` applies only to Wappa Inbox credential encryption.
  Hosts must not reuse it for unrelated data.

An authentication or context-validation failure is a credential-store
integrity error. Wappa fails closed, logs no ciphertext or plaintext, and does
not send a Meta request.

**Answer:** Agreed. Explicit multi-Inbox mode requires
`SYSTEM_TOKEN_ENC_KEY`, and Wappa owns Inbox credential encryption and
decryption across durable storage and the Inbox Directory. Host Applications
must use Wappa's credential creation and rotation methods before persistence,
return `EncryptedSecretEnvelope` values through `IInboxDirectorySource`, and
never decrypt them. They cannot replace the codec or alter the encrypted row
shape. The active-plus-previous rotation contract is resolved in 2e.1.

### 2e.1. How does `SYSTEM_TOKEN_ENC_KEY` rotate?

Changing the encryption secret affects durable Host Application rows as well as
the directory cache. Losing every decryption secret makes persisted Inbox
credentials unrecoverable. A rolling deployment can also leave old and new
workers unable to read one another's records.

**My recommendation:** Add an optional previous-secret ring while keeping
`SYSTEM_TOKEN_ENC_KEY` as the active encryption secret. Wappa encrypts with the
active secret and may decrypt with active plus previous secrets. A successful
cache read under a previous secret rewrites the cache row under the active
secret, but it cannot mutate the host database. Wappa therefore exposes a
record-rotation method that accepts an old encrypted canonical record and
returns the same record re-encrypted with the active secret. The Host
Application enumerates its own rows, calls that method, and persists the
returned records without seeing plaintext. Remove a previous secret only after
the durable migration, maximum 60-minute directory TTL, and rollout window have
all completed. `MultiFernet` directly supports this first-encrypt,
try-all-decrypt behavior and token rotation.

**Answer:** Agreed. The active setting remains `SYSTEM_TOKEN_ENC_KEY`. Optional
previous secrets use `SYSTEM_TOKEN_ENC_PREVIOUS_KEYS` as an ordered,
comma-separated Fernet key ring. Wappa encrypts with the active key and tries
the active key followed by previous keys when decrypting. A successful cache
read under a previous key rewrites the cached envelope with the active key.

Wappa exposes `rotate_encrypted_record(record)`, which decrypts internally and
returns the same canonical record re-encrypted with the active key. The Host
Application enumerates and persists its own durable rows without receiving
plaintext. Operators remove a previous key only after durable re-encryption,
the maximum 60-minute directory TTL, and the deployment overlap window have
all completed. Losing every accepted key makes the affected durable credentials
unrecoverable. Key rotation is a v0.27 release blocker.

### 2f. Does `is_active=False` remain a record or become a deletion?

**My recommendation:** Keep a short-lived inactive tombstone with the new
`credential_version`. It makes deactivation immediately reject without a DB
lookup and prevents an older concurrent writer from resurrecting credentials.
After an agreed retention window, Wappa may remove the row and indexes.

**Answer:** Agreed. Keep an inactive or absent negative record for a fixed
60-minute TTL. Reads do not renew that TTL. A higher-version successful
`refresh_inbox(inbox_ref)` may replace it immediately.

## 3. Redis cache, PostgreSQL authority, and freshness

### 3a. Is Redis the runtime authority or only a cache?

There are two valid designs:

1. **Runtime directory:** the host commits its DB transaction, then publishes
   the validated record to Wappa. A Redis miss means unknown Inbox.
2. **Read-through cache:** Wappa calls a host-supplied source adapter on a miss,
   validates the returned record, and fills Redis.

**My recommendation:** Use the read-through model. Redis handles the active hot
path. On a miss, Wappa asks the Host Application's persistent source adapter for
the record, validates it against Wappa's Pydantic model, and writes it through
the concrete `InboxDirectoryTable`, which uses the system-scoped `ITableCache`.
Wappa owns that sequence; the host owns its database schema and the query that
maps it to the Wappa record.

**Answer:** Agreed. Redis is a read-through cache for the application-scoped
Inbox Directory. The Host Application's database remains durable authority.
Wappa controls validation and cache population after the first database lookup.

### 3b. What happens on a Redis miss for a known DB Inbox?

**My recommendation:** Call the persistent source adapter. A returned record is
validated and cached before the original operation continues. A confirmed
missing or inactive record maps to the caller-facing unknown-Inbox result; a DB
or adapter failure maps to `503`. Never treat cache absence alone as proof that
an Inbox does not exist.

**Answer:** Mechanism agreed. A Redis miss triggers the first DB lookup and
cache population. The exact status for a confirmed missing record remains part
of question 9a.

### 3c. Do credential records expire by TTL?

The current five-minute TTL can allow an active token to disappear and can also
keep a deactivated token usable until expiry.

**My recommendation:** Set a 60-minute sliding TTL. Every successful directory
hit renews the record for another 60 minutes. An Inbox used continuously stays
hot; an Inbox with no lookup for a full hour expires and reloads from the Host
Application's persistent source on its next use. Deactivation still needs an
explicit invalidation path because waiting for silence is not revocation.

**Answer:** Agreed. The TTL is 60 minutes and renews on every successful hit.
Only 60 minutes of total lookup silence removes the cached key.

### 3d. What is the write ordering for onboarding and rotation?

**My recommendation:** Commit the host database first, then upsert the Wappa
directory with a higher `credential_version`, then evict the MessengerFactory
client for that Inbox. A directory write failure leaves the durable record
ahead and is recoverable by reconciliation. Writing Redis first could expose
credentials for a business transaction that later rolls back.

**Answer:** Agreed. The host commits first and then calls
`refresh_inbox(inbox_ref)`. Wappa reloads through `IInboxDirectorySource`,
rejects stale versions, updates the directory projection, repairs reverse-index
membership, and evicts the cached Messenger. The command raises on failure and
is safe to retry.

### 3e. What is the write ordering for deactivation?

**My recommendation:** Commit deactivation in the host DB, immediately write an
inactive versioned tombstone to Wappa, remove the Inbox from reverse indexes,
and evict MessengerFactory. Treat failure to update Wappa as an operational
incident and retry through an outbox/reconciler. TTL alone is not an acceptable
revocation mechanism.

**Answer:** Agreed. The host commits the higher-version inactive state and then
calls `refresh_inbox(inbox_ref)`. Wappa writes the fixed-TTL negative record
before removing reverse-index membership and evicting the cached Messenger.
Retrying the same version completes unfinished derived work. Active-record
sliding TTL never defines revocation.

### 3f. Must hosts implement an outbox?

**My recommendation:** No mandatory outbox in v0.27.0. Define the command and
idempotency contract so an outbox can call it safely, and provide a full
reconciliation operation. Document an outbox as the recommended production
integration when credential activation/deactivation cannot tolerate a split
brain.

**Answer:** Agreed. Wappa does not require an outbox. The refresh command is
idempotent and raises on failure so a direct caller or a Host Application outbox
can retry it. A bulk reconciler, if supplied later, must call the same command
instead of creating another directory write path.

## 4. WABA reverse lookup and membership

### 4a. Should account lookup use a composite identity?

The current method accepts only `platform_account_id`. Account identifier
spaces can collide across Platforms, just as Inbox identifier spaces can.

**My recommendation:** Introduce
`PlatformAccountRef(platform, platform_account_id)`. The Host Application's
source method returns complete canonical records so Wappa can validate and
cache them:

```python
IInboxDirectorySource.list_inboxes_for_platform_account(
    account_ref: PlatformAccountRef,
) -> tuple[InboxCredentialRecord, ...]
```

Wappa's internal resolver returns global Inbox identities:

```python
IInboxCredentialResolver.list_inbox_refs_for_platform_account(
    account_ref: PlatformAccountRef,
) -> tuple[InboxRef, ...]
```

For WhatsApp, the payload router constructs the reference with
`PlatformType.WHATSAPP` and `entry[].id`. The Host Application does not return
bare IDs or decide membership filtering.

**Answer:** Agreed. `PlatformAccountRef` is the canonical cross-Platform
identity. Account lookup receives that reference and returns `InboxRef` values.
The source adaptation point returns complete canonical credential records,
including Wappa-encrypted secret envelopes on active records. Wappa validates
them, decides active membership, and builds the index.

### 4b. How is the one-account-to-many-Inboxes lookup stored?

`find_by_field()` cannot implement this lookup. It returns one row and is not
part of `ITableCache`. A raw Redis Set would also violate the decision that the
directory works through the existing Table Cache contract across Redis, memory,
and JSON backends.

**My recommendation:** Store a status-discriminated, Wappa-owned typed index
row under the system-scoped Table Cache:

```python
class PlatformAccountActiveIndexRecord(BaseModel):
    schema_version: Literal[1] = 1
    status: Literal["active"] = "active"
    account_ref: PlatformAccountRef
    inbox_refs: tuple[InboxRef, ...]
    index_version: PositiveInt
    refreshed_at: datetime


class PlatformAccountEmptyIndexRecord(BaseModel):
    schema_version: Literal[1] = 1
    status: Literal["empty"] = "empty"
    account_ref: PlatformAccountRef
    index_version: PositiveInt
    checked_at: datetime
```

The storage coordinates are:

```text
context_id = "__system__"
table_name = "wappa_inbox_directory_account_index"
pkid       = PlatformAccountRef.cache_namespace
```

An active row stores sorted, duplicate-free `InboxRef` members and uses the
agreed sliding 60-minute TTL. `index_version` belongs to this cached projection;
it is separate from each Inbox record's `credential_version`. Concurrent
writers use `create_if_absent()` and
`replace_if(expected={"index_version": current_version})`, with a bounded
retry on conflict.

`refresh_inbox(inbox_ref)` writes the canonical Inbox row first. It then repairs
the new Platform Account index and, when the previous membership is known, the
old index. `ITableCache` guarantees one-row transitions, not one transaction
across all directory rows. Retrying the refresh command with the same
`credential_version` completes unfinished index work.

**Answer:** Agreed. Use the typed Table Cache index above. Do not use a raw
Redis Set or add a directory-specific Redis interface. Wappa owns the models,
sorting, duplicate removal, compare-and-replace loop, TTL rules, and storage
names.

### 4c. Is the reverse index itself authoritative?

**My recommendation:** No. Every index result must be checked against canonical
Inbox records. Each record must exist, be active, and match the requested
Platform Account Reference.

If every member passes, Wappa renews the active index and member-record TTLs and
returns the sorted references. A missing, inactive, or wrongly assigned member
marks the index as stale. Wappa then calls the source once, validates its full
result, rebuilds the directory projection, and returns only after repair
succeeds. Source or repair failure returns `503`; dispatching a known subset
could drop a legitimate account-scoped delivery.

An index cannot detect an omitted active member when all listed members remain
valid. Onboarding, movement between Platform Accounts, reactivation, and
deactivation therefore call the idempotent `refresh_inbox(inbox_ref)` command.
The command raises on failure so the Host Application can retry it directly or
through an outbox. A later reconciler must call the same command.

**Answer:** Agreed. The reverse index is a cached projection, never membership
authority. Wappa validates every member. Detected corruption triggers one
synchronous source reload and index repair. Any indeterminate or failed repair
returns `503`, and Wappa dispatches nothing from that request.

### 4d. Must a phone-scoped payload prove WABA membership?

The current implementation validates that `phone_number_id` names an active
Inbox but does not prove that the record belongs to `entry[].id`. A payload can
therefore pair a known phone Inbox with the wrong WABA.

**My recommendation:** Yes. WhatsApp routing must resolve
`InboxRef(PlatformType.WHATSAPP, phone_number_id)`, require an active record,
and compare that record's Platform Account Reference with
`PlatformAccountRef(PlatformType.WHATSAPP, entry[].id)`. It performs this check
before constructing any Dispatch Context.

A mismatch is a `400` payload-routing contract failure. It is not `401` because
Wappa has already authenticated the POST callback with the Meta App Secret.
Wappa rejects the complete batch and dispatches nothing.

**Answer:** Agreed. Every phone-scoped change must prove active Inbox-to-WABA
membership. A mismatch returns `400` before any Dispatch Context or handler work
exists. This closes a gap in the current router, which checks conflicting IDs
inside the payload but does not compare the phone's stored membership with
`entry[].id`.

### 4e. What does an empty WABA index mean?

**My recommendation:** Distinguish a confirmed empty Platform Account from an
indeterminate lookup. On an index miss, Wappa calls the source once. A
successful result with zero active members writes
`PlatformAccountEmptyIndexRecord` with a fixed 60-minute TTL and returns `400`.
Hits do not renew an empty index. A later successful
`refresh_inbox(inbox_ref)` replaces it immediately when an Inbox activates.

A source timeout, database failure, invalid record, encryption/configuration
error, or failed index repair returns `503`. Wappa does not write an empty index
for those failures. It never chooses `WP_PHONE_ID`, a default Inbox, or the
first available Inbox.

Credential activity and deactivation reads should use the primary database
unless the Host Application explicitly accepts replica lag in its source
adapter.

**Answer:** Agreed. Confirmed zero active members returns `400` and receives a
fixed-TTL negative index whose hits do not renew it. An unavailable or
indeterminate source returns `503` without negative caching. No fallback Inbox
exists.

## 5. Meta application credentials and callback authentication

### 5a. Is one Wappa process bound to one Meta App Secret?

HMAC verification must happen before parsing. A payload does not provide a
trusted App ID that can safely choose its verification secret first.

**My recommendation:** Bind one Wappa application to exactly one Meta App
configuration: App Secret, verify token, and Graph API version. It may serve
many WABAs and many Inboxes registered under that Meta App. Do not try several
secrets, select a secret from payload contents, or add callback routing between
Meta Apps. A Host Application that needs another Meta App runs another Wappa
application instance with its own configuration.

**Answer:** Agreed. One Meta App per Wappa application is a permanent boundary,
not a v0.27 limitation awaiting a multi-App design. Wappa supports many WABAs
and Inboxes under that one Meta App. It does not support several Meta Apps
inside one Wappa application.

### 5b. Where does the App Secret come from in legacy and explicit modes?

Current code has no `WP_APP_SECRET`. `WhatsAppProcessor` incorrectly uses
`WP_WEBHOOK_VERIFY_TOKEN` as the HMAC secret for POST signature validation.
Meta's GET challenge verify token and POST App Secret are different
credentials and cannot share one setting.

**My recommendation:** Define one immutable, Wappa-owned application value:

```python
class MetaApplicationConfig(BaseModel):
    app_secret: SecretStr
    whatsapp_webhook_verify_token: SecretStr
    graph_api_version: str
    graph_base_url: AnyHttpUrl
```

Wappa accepts this value through exactly one configuration path. A Host
Application may supply it during Wappa construction, or Wappa's settings
adapter may build it from:

```text
META_APP_SECRET          -> app_secret
WP_WEBHOOK_VERIFY_TOKEN  -> whatsapp_webhook_verify_token
META_API_VERSION         -> graph_api_version
META_BASE_URL            -> graph_base_url
```

Supplying an explicit object while any corresponding environment authority is
also configured fails startup. Wappa does not apply precedence between two
application configurations.

The same contract applies in both Inbox routing modes:

```text
Legacy single-Inbox mode
  MetaApplicationConfig
  WP_ACCESS_TOKEN + WP_PHONE_ID + WP_BID

Explicit multi-Inbox mode
  MetaApplicationConfig
  SYSTEM_TOKEN_ENC_KEY + IInboxDirectorySource
```

`META_APP_SECRET` is the correct setting name because the secret belongs to the
Meta App. It is separate from the per-Inbox access token and from the arbitrary
token chosen for Meta's GET challenge. It never appears in an Inbox Credential
Record or the Inbox Directory. `SYSTEM_TOKEN_ENC_KEY` does not encrypt it;
the Host Application supplies it at runtime through its environment or secret
manager. Wappa keeps it redacted and exposes only configured or not configured
health information.

Symphonai declares `META_APP_SECRET` once in the process environment. Its Meta
Marketing API integration and Wappa can read the same environment value because
both use the same Meta App. Wappa's settings adapter reads it directly through
the environment-backed configuration path. Symphonai does not need to add the
field again for Wappa, copy the value into a Wappa-specific alias, or pass an
explicit `MetaApplicationConfig` to Wappa. Doing the last of those while the
environment value exists would violate the single-configuration-source rule.
Symphonai's existing Marketing API settings may continue reading the same
environment variable for their own use.

`META_APP_ID` remains a Host Application setting unless Wappa later needs the
ID for an actual Meta operation. `META_ADS_CONFIG_ID` belongs only to
Symphonai's Marketing API and does not enter Wappa configuration.

**Answer:** Agreed. Wappa owns `MetaApplicationConfig` and accepts exactly one
source for it. The application configuration is independent of legacy or
explicit Inbox routing. Both modes use `META_APP_SECRET` for POST callback
authentication. The App Secret remains application-scoped and never enters
per-Inbox storage. Symphonai keeps one environment declaration that Wappa reads
directly; the Wappa integration does not duplicate the setting in application
code. Its Ads configuration remains outside Wappa.

### 5c. What are the signature failure semantics?

**My recommendation:** Read raw bytes once, require `X-Hub-Signature-256`, use
constant-time comparison, and reject missing/malformed/mismatched signatures
with `401` before JSON decoding, credential lookup, logging payload contents,
or scheduling work. Preserve the raw-body snapshot for later parsing.

**Answer:** Agreed. Wappa reads the raw request bytes once and requires a
well-formed `X-Hub-Signature-256` value. It computes HMAC-SHA256 with
`META_APP_SECRET` and compares the digest in constant time. A missing,
malformed, or mismatched signature returns the same generic `401` response.
Wappa performs no JSON decoding, credential lookup, payload-content logging, or
work scheduling before authentication succeeds. The raw-body snapshot then
feeds JSON parsing so verification and parsing use the same bytes.

### 5d. Should HMAC validation be optional in development?

**My recommendation:** Do not provide a bypass. If the Host Application mounts
the WhatsApp callback, startup requires `META_APP_SECRET` and
`WP_WEBHOOK_VERIFY_TOKEN` in every environment. `SYSTEM_ENVIRONMENT=DEV` does
not change POST authentication. Local tests, fixtures, and manual webhook tools
must sign the exact request bytes with a development App Secret.

An outbound-only Host Application that does not mount the WhatsApp callback
does not need callback credentials. The requirement follows the installed HTTP
capability. Wappa must remove the current behavior that accepts a webhook when
the verification setting is absent. It must not add a
`DISABLE_WEBHOOK_SIGNATURE_VALIDATION` setting.

**Answer:** Agreed. Wappa has no HMAC bypass, including development. A mounted
WhatsApp callback cannot start without both application callback secrets.
Unsigned or incorrectly signed requests never enter payload routing. Tests and
local tools create valid signatures instead of weakening the runtime contract.

## 6. `X-Wappa-Inbox-ID` and the full WhatsApp HTTP surface

The header means: "execute this Inbox-dependent operation using the credential,
Meta phone number, Platform Account, caches, identity resolver, and event scope
of this Inbox." It does not only select the sender for message delivery.

### Current operation inventory

| Operation family | Current routes | Why Inbox is or is not needed |
|---|---|---|
| Text and receipt transport | send text; mark message read/typing | Selects Meta `phone_number_id`, token, and outbound event scope. |
| Media transport | send image, video, audio, document, sticker | Selects Meta `phone_number_id`, token, media handler, and event scope. |
| Interactive transport | send buttons, list, CTA, plus two example send endpoints | Selects Meta `phone_number_id`, token, and event scope. |
| Specialized transport | send contact, location, location request | Selects Meta `phone_number_id`, token, and event scope. |
| Template transport | send text-header, media-header, and location-header Templates | Selects Inbox credentials and the template transport scope. |
| Media service | upload, get info, download, delete | Uses the selected Inbox's token; upload/delete also mutate Meta assets. |
| Template service | get by ID/name, list, namespace | Uses the Inbox token and its `platform_account_id` (WABA). |
| WhatsApp health | service health | Constructs the Inbox-scoped Meta client and handlers. |
| State Handler API | set, get, delete | Does not call Meta, but reads or mutates Wappa state scoped by Inbox and User. |
| Local validation | validate contact; validate coordinates | Pure local validation; no Inbox data. |
| Static/local limits | text, media, interactive, and Template limits | Pure local values/factories; no Inbox data. |

### 6a. Which rule should control header requirements?

**My recommendation:** Require `X-Wappa-Inbox-ID` for every route that touches
Meta or Inbox-scoped Wappa state. Do not require it for pure local validation,
static limits, root health, docs, or OpenAPI. Encode this as route metadata or a
dependency attached to capability routers, not as a growing path allowlist in
global middleware.

**Answer:** Agreed. Require the header for every route that calls Meta, reads or
mutates Inbox-scoped Wappa state, resolves a Platform Account through an Inbox,
or constructs Inbox-specific health. Pure local validation, static limits,
root health, docs, and OpenAPI do not resolve an Inbox. Attach the requirement
to capability routers or route dependencies; remove the broad
`/api/whatsapp/*` decision from global middleware.

### 6b. Does the header authorize the operation?

**My recommendation:** No. It selects runtime scope and proves only that Wappa
knows an active Inbox. Host authentication/authorization must decide whether
the caller may operate that Inbox. Document this sharply because a valid Inbox
ID in a header is not a security credential.

**Answer:** Agreed. The header selects runtime scope and proves only that Wappa
knows an active Inbox. It is not a credential and grants no permission. The
Host Application or Wappa authentication plugin authorizes the caller before
Wappa resolves the Inbox Execution Context.

### 6c. Should local-only routes ignore or reject a supplied header?

**My recommendation:** Ignore it and do not bind Inbox context for that route.
A validation result or static limit should not change based on an unrelated
header, and an unavailable credential directory should not take those local
routes down.

**Answer:** Agreed. A local-only route ignores the header and does not bind or
validate Inbox context. An invalid or unknown header therefore cannot make
static limits or local validation depend on the Inbox Directory.

### 6d. Should media downloads require Inbox even if Meta's temporary URL is
unauthenticated?

**My recommendation:** Yes. Wappa first calls Meta for media metadata using the
selected Inbox credential, and media objects belong to a Platform context. The
subsequent byte download may use an unauthenticated HTTP client, but the
operation began with Inbox-scoped authorization.

**Answer:** Agreed. Media download is Inbox-dependent because Wappa uses the
selected Inbox credential to resolve the Meta media object before downloading
its bytes.

### 6e. Should Template info resolve WABA through the Inbox record?

**My recommendation:** Yes. The caller supplies only the Inbox header. Wappa
loads the canonical record and supplies its `platform_account_id` to the Meta
Template endpoints. The caller must not send a second WABA ID that can disagree
with the selected Inbox.

**Answer:** Agreed. The caller supplies only `X-Wappa-Inbox-ID`. Wappa combines
it with the WhatsApp route Platform, resolves the canonical Inbox Credential
Record, and obtains the WABA from `platform_account_id`. Template routes do not
accept a second caller-supplied WABA ID.

### 6f. Should the two example interactive send endpoints remain production
routes?

`/send-complex-buttons` and `/send-menu-list` contain hard-coded demonstration
content but are mounted as real outbound capabilities.

**My recommendation:** Remove them from the library's HTTP contract and keep
their code in examples. They enlarge an unauthenticated mutation surface and
do not add a distinct runtime capability.

**Answer:** Agreed. Remove `/send-complex-buttons` and `/send-menu-list` from
the production HTTP contract. Keep their hard-coded demonstrations in examples
or documentation. They do not define separate runtime capabilities.

### 6g. Should all Inbox-dependent routes perform both middleware validation
and client-factory validation?

**My recommendation:** Resolve one validated `InboxExecutionContext` at the HTTP
boundary and reuse it through dependencies. Avoid a second store round-trip in
`get_whatsapp_client`. Internal non-HTTP entry points still validate through
their own boundary. This removes duplicated work without trusting a raw header.

**Answer:** Agreed. Resolve one validated `InboxExecutionContext` at the HTTP
boundary and reuse it through dependencies. It contains the qualified
`InboxRef` and internal route capabilities, not a caller-visible access token.
Middleware, dependencies, and `get_whatsapp_client()` must not each repeat the
directory lookup. Internal non-HTTP entry points validate at their own
boundaries.

## 7. Legacy single-Inbox coexistence

### 7a. Is `WP_PHONE_ID` still a default only, never an authority?

**My recommendation:** Yes. In legacy settings mode it populates the sole
`WhatsAppInboxCredentialRecord` and supplies `default_inbox_id` for HTTP calls
that omit the header. After that adapter boundary, the runtime uses the same
Inbox record and execution path as explicit mode. No middleware, Messenger,
cache, event, or webhook component reads `WP_PHONE_ID` directly.

**Answer:** Agreed. In legacy mode `WP_PHONE_ID` supplies the single default
Inbox through the settings adapter only. Explicit mode does not consult it.

### 7b. Can a legacy-mode request override `WP_PHONE_ID` with a header?

The current middleware accepts a header first, then validates it against the
single-Inbox settings store, so only the same ID succeeds.

**My recommendation:** Preserve that behavior. The header may explicitly name
the configured Inbox but cannot introduce a second one. This keeps one rule:
the directory validates every selected Inbox.

**Answer:** Agreed. The header may explicitly repeat the one configured Inbox
ID. A different value fails directory validation with `404` and cannot create a
second legacy Inbox. Omitting the header selects the settings-backed default.

### 7c. What happens when both a complete environment bundle and an explicit
directory are configured?

The earlier recommendation let `explicit` select the directory and ignore the
Inbox environment bundle with a warning.

**Revised recommendation:** Fail explicit-mode startup when any of
`WP_ACCESS_TOKEN`, `WP_PHONE_ID`, or `WP_BID` is present. A warning still leaves
two credential sources configured and invites operators to believe the
environment token is active. `legacy` explicitly selects settings. Replace
ambiguous `auto` precedence with a build-time resolved enum whose value is
visible in health output.

**Answer:** Agreed. Remove `auto` and expose
`InboxRoutingMode.LEGACY = "legacy"` and
`InboxRoutingMode.EXPLICIT = "explicit"`. An omitted mode defaults to legacy
for existing single-Inbox consumers.

Legacy mode requires the complete `WP_ACCESS_TOKEN + WP_PHONE_ID + WP_BID`
bundle and rejects an `IInboxDirectorySource`. Explicit mode requires
`IInboxDirectorySource + SYSTEM_TOKEN_ENC_KEY` and rejects any legacy Inbox
credential variable. A source supplied without explicit mode fails with a
configuration message. Health output reports the selected mode; warnings and
silent precedence do not select an authority.

## 8. `db` and `db_read`: the contract we actually expose

### 8a. Are the current names correct?

`db` is primary-preferred and may read or write. `db_read` is replica-preferred
and should be used only for reads; it falls back to primary when no replica is
available.

**My recommendation:** Keep `db` and `db_read` to avoid a low-value public
rename. Document them as `primary session factory` and `read-only intent session
factory`. Renaming `db` to `db_write` would imply the primary cannot be used for
consistent reads after a write.

**Answer:** Agreed. Keep `db` as the Primary Session Factory and `db_read` as
the Read-Intent Session Factory. `db` supports writes and primary-consistent
reads. Do not rename it to `db_write`.

### 8b. Should Wappa inject a `DatabaseSessions` façade instead of two
callables?

**My recommendation:** Not yet. The two async context-manager factories are
small ports and easy to substitute in tests. A façade that only forwards
`.primary()` and `.read()` fails the deletion test. Introduce one only when it
can own a real policy such as consistency mode, transactions spanning
repositories, or replica telemetry.

**Answer:** Agreed. Keep the two async context-manager factories. Do not add a
forwarding façade. Reconsider a richer object only if it owns a real policy the
session manager does not already own.

### 8c. Is `db_read` technically read-only today?

No. It returns a normal `AsyncSession`, uses the same `auto_commit` setting, and
can execute writes if the database role permits them.

**My recommendation:** Use a read-only database role for replica URLs and have
Wappa start a PostgreSQL read-only transaction before yielding `db_read`. Apply
the transaction rule to a primary fallback session as well. A database role and
transaction enforcement protect different failure paths; a coding convention
alone is too weak.

**Answer:** Agreed as the hardened target. `db_read` must start a read-only
transaction on a replica or primary fallback. Replica URLs should also use
database roles without write privileges. Code that writes through `db_read`
must move to `db`. The implementation belongs to the PostgreSQL plugin
hardening PRD and must not be claimed as current v0.27 behavior before it lands.

### 8d. Should primary fallback be silent?

**My recommendation:** Keep fallback as the default availability policy, but
make it observable and configurable. Add `read_fallback="primary" | "error"`.
Expose `configured_replicas`, `healthy_replicas`, and fallback count in health
or metrics. Applications that must protect the primary can choose `error`.

**Answer:** Agreed. Add `ReadFallbackPolicy.PRIMARY` and
`ReadFallbackPolicy.ERROR`, with `PRIMARY` as the compatibility default. Health
or metrics report configured replicas, available replicas, active primary
fallback, and a fallback counter. The implementation belongs to the PostgreSQL
plugin hardening PRD.

### 8e. What happens when a replica fails after startup?

Current startup removes unhealthy replicas. A later acquisition failure retries
the same selected engine and does not rotate to another replica.

**My recommendation:** Before the caller executes a query, a transient
connection-acquisition failure may safely try the next replica, then apply the
configured primary/error fallback. Never replay a query or transaction after it
has begun. Track failures so an unhealthy replica is cooled down before it
re-enters rotation.

**Answer:** Agreed. A transient failure while acquiring a connection may try
the next replica, then apply the configured fallback policy, because no caller
query has run. After Wappa yields a session, it never replays a query or
transaction. A failed replica enters a bounded, configurable cooldown before
round-robin selection can use it again. Implement this in the PostgreSQL plugin
hardening PRD.

### 8f. What consistency does `db_read` promise?

**My recommendation:** Eventual consistency only. Code that writes and then
must observe that write uses `db` for both operations in the same transaction
or on the primary. Do not make a replica sticky to an Inbox or User; that does
not guarantee replay position and creates accidental coupling between runtime
identity and database topology.

**Answer:** Agreed. `db_read` promises eventual consistency only. A caller that
writes and must observe that write uses `db`, preferably inside one
transaction. Wappa does not make replicas sticky to an Inbox or User.

### 8g. Should credential-directory recovery read from `db_read`?

**My recommendation:** No by default. Activation, token rotation, and
deactivation are security-sensitive and replica lag can revive an old token or
active flag. Reconciliation and any cache-miss source adapter should read the
primary unless a host explicitly accepts bounded staleness.

**Answer:** Agreed. Inbox credential cache misses, refresh after activation or
rotation, deactivation, and reconciliation use the primary through the Host
Application's source adapter. A host that chooses a replica for this source
explicitly accepts the security and freshness risk; it is not Wappa's default
contract.

### 8h. Should `auto_commit` apply to `db_read`?

**My recommendation:** Separate the teardown policies. Primary sessions may
auto-commit on success. Read-intent sessions should close with rollback/end of
transaction and never issue a commit as their normal success path. This makes
intent visible and avoids normalizing writes through `db_read`.

**Answer:** Agreed as the hardened target. Primary `db` sessions retain their
configured auto-commit behavior. Read-intent sessions end or roll back their
read-only transaction on success and roll back on failure. They never commit as
their normal teardown path. Implement this with the read-only transaction work
in the PostgreSQL plugin hardening PRD.

### 8i. Is database availability part of every Dispatch Context?

Today `db` and `db_read` are optional and injected into webhook, API, external
webhook, and cron handler clones when the plugin is installed.

**My recommendation:** Keep them optional capabilities. Fail with one clear
runtime error when a handler tries to use an absent factory; do not install a
Null Object that returns a fake session. Ensure all dispatch paths use the same
context builder so API, webhook, cron, and external events do not drift.

**Answer:** Agreed. `db` and `db_read` remain optional factories typed as
`SessionFactory | None`. Wappa does not install a fake session factory. Every
webhook, API, cron, and external-event Dispatch Context uses the same context
builder. A handler can check for `None`; Wappa may provide a small
`require_database()` helper for a clear error.

### 8j. Does Wappa promise database-level Inbox isolation?

**My recommendation:** No. Wappa scopes its runtime dependencies by Inbox, but
the PostgreSQL plugin supplies sessions, not row-level business authorization.
Host repositories must include their own Inbox or business-owner filters and
invariants. State this explicitly so `self.db` is not mistaken for an
Inbox-filtered repository.

**Answer:** Agreed. Wappa supplies sessions and does not add Inbox predicates,
Owner authorization, PostgreSQL row-level security, or Host Application
repository invariants. Host repositories own those filters and checks.

## 9. Failure semantics and atomic intake

### 9a. What status codes distinguish caller errors from infrastructure errors?

**My recommendation:** Use:

- `400` for malformed JSON, non-object payload roots, invalid Inbox ID format,
  WABA/Inbox mismatch, and structurally unroutable authenticated payloads.
- `401` for missing or invalid Meta HMAC signatures.
- `404` for a caller-selected HTTP Inbox that the healthy directory confirms is
  unknown/inactive.
- `503` for directory unavailability, missing runtime population, Redis
  failure, or credential resolution failure after boundary validation.

Fix the current path where JSON arrays/scalars become `503` through an
`AttributeError` caught as a credential-store outage.

**Answer:** Agreed. Use `400` for malformed JSON, non-object roots, invalid
Inbox format, a confirmed unknown or inactive payload Inbox, WABA membership
mismatch, a confirmed empty WABA, and other structurally unroutable
authenticated payloads. Use `401` only for a missing or invalid Meta signature.
Use `404` when an HTTP caller selects an Inbox that the healthy directory
confirms is unknown or inactive. Use `503` for directory, Redis, source,
credential decryption, or runtime dependency unavailability. Reserve `500` for
an unexpected Wappa defect. Fix the current array/scalar path and the current
`401` mapping for unknown payload Inboxes.

### 9b. Must a batched webhook remain all-or-nothing before scheduling?

**My recommendation:** Yes. Authenticate raw bytes, validate the JSON root,
split every entry/change, resolve every Inbox, verify WABA membership, and build
every Dispatch Context before submitting any delivery. A failure in item N
must not leave items 1..N-1 scheduled.

**Answer:** Agreed. Wappa authenticates the exact bytes, validates an object
root, splits every entry and change, resolves every Inbox Reference, proves
WABA membership, and builds every Dispatch Context before scheduling any
delivery. Failure in item N schedules none of items 1 through N-1.

### 9c. Should Wappa deduplicate WABA fan-out deliveries?

**My recommendation:** Keep at-least-once delivery and deterministic fan-out in
v0.27.0. Do not deduplicate and do not invent a generic fingerprint yet. Batch
positions may change when Meta repackages a delivery, while a canonical payload
hash can collapse two legitimate identical events. Hosts should use
Platform-supplied identifiers where available. A later delivery-identity PRD
must distinguish one logical Platform change from its per-Inbox deliveries.

**Answer:** Agreed. Wappa performs no webhook deduplication and supplies no
generic delivery fingerprint in v0.27. Host handlers remain idempotent under
Meta retries, batch splitting, and WABA fan-out. Delivery identity receives a
separate design before Wappa claims a stable identifier.

### 9d. Should a credential-store failure during Messenger construction remain
an unclassified `500`?

**My recommendation:** No. Normalize directory/credential dependency failures
at every boundary to one typed `InboxDirectoryUnavailableError`, mapped to
`503` by HTTP adapters and recorded in background-delivery results. Do not catch
all exceptions as "unknown Inbox."

**Answer:** Agreed. Introduce typed directory failures including
`InboxNotFoundError`, `InboxMembershipError`,
`InboxDirectoryUnavailableError`, and `InboxCredentialIntegrityError`. HTTP
adapters map them to the agreed status matrix. Messenger construction must not
turn a directory outage into an unclassified `500` or report it as an unknown
Inbox. Background work records the typed failure when no HTTP response remains.

## 10. Terminology, module ownership, and the v0.27 cut line

### 10a. Is **Platform** still the canonical Wappa term?

The current `CONTEXT.md` says Platform and forbids `provider` as a code
identifier. The supplied repository instructions say Provider is canonical.
Both cannot govern the same change.

**My recommendation:** Keep **Platform**, matching the earlier DDD decision and
current code (`PlatformType`, `platform_account_id`). Update the repository
instructions after this decision so future agents do not repeatedly reopen it.

**Answer:** Agreed. Platform remains Wappa's canonical term, matching the
existing DDD decision and `PlatformType` vocabulary.

### 10b. Where does `InboxDirectory` live?

**My recommendation:** Keep domain identity, credential models, ports, and
typed failures under `wappa/domain/inbox/`. Put read-through resolution,
refresh, membership, and version orchestration in the domain-service layer.
Place the concrete system-scoped `InboxDirectoryTable` under persistence; it
depends on `ITableCache`, not Redis. Keep Fernet envelope work under
`wappa/core/security/`. WhatsApp maps `phone_number_id`, WABA ID, and resolved
credentials at its Platform boundary. The API receives an Inbox Execution
Context and knows nothing about Table Cache names, source queries, encryption,
or token values.

**Answer:** Agreed. Use this dependency direction. Do not introduce a
directory-specific Redis adapter. Memory, JSON, and Redis conformance tests use
the same `ITableCache`-backed `InboxDirectoryTable` behavior.

### 10c. Does Wappa own the host PostgreSQL table and migration?

**My recommendation:** No. Wappa owns the Pydantic runtime record, Redis
directory format, commands, and conformance behavior. The Host Application owns
its durable business schema and maps it to Wappa's record. Remove the current
claim that hosts should reproduce a Wappa SQL table shape; that couples Wappa
to a host's database and duplicates schema ownership.

**Answer:** Agreed. The Host Application owns its DB tables and migrations.
Wappa owns the Pydantic cache record and the rules for validating, storing,
renewing, and resolving it. Each host maps its own schema to that record through
the persistent source adapter.

### 10d. Which hardening items are release blockers for v0.27.0?

**My recommendation:** Block release on:

1. Correct Meta HMAC verification and `MetaApplicationConfig`.
2. `InboxRef` and `PlatformAccountRef` across routing and cache namespaces.
3. Wappa-owned encrypted credential records plus encryption-key rotation.
4. Mandatory `InboxDirectoryTable` and `IInboxDirectorySource` contracts.
5. Cached WABA reverse lookup and phone-to-WABA membership proof.
6. Route-level Inbox requirements and one resolved Inbox Execution Context.
7. Explicit `legacy` and `explicit` Inbox Routing Modes.
8. Stable failure mapping and all-or-nothing webhook intake.
9. Rotation, deactivation, stale-version, reverse-index, mixed-batch, and route
   matrix tests.
10. Updated DDD, public contract, examples, migration notes, and Symphonai
    adoption PRD.

Keep read-replica cooldown, strict fallback, enforced read-only transactions,
replica telemetry, and delivery identity in separate PRDs. They do not block
v0.27 unless release documentation claims those behaviors already exist.

**Answer:** Agreed. Every item in the blocker list must land before v0.27 ships.
`SYSTEM_TOKEN_ENC_PREVIOUS_KEYS` support and durable record re-encryption are
part of the credential blocker. PostgreSQL replica hardening and delivery
identity remain separately planned work and must be described as such.

### 10e. Which documentation must change with the implementation?

**My recommendation:** In the same feature series, update:

- root `CONTEXT.md` with Inbox Directory, Inbox Credential Record, and the
  resolved Platform terminology;
- root and persistence/plugin `ARCHITECTURE.md` files with scope and dependency
  direction;
- `docs/public-contract.md` with the record, commands, header matrix, legacy
  path, failures, and rotation/deactivation protocol;
- ADR-0010 for authenticated payload routing and WABA membership;
- a new ADR for the application-scoped, 60-minute sliding read-through Inbox
  Directory, because that choice changes cache scope and operational ownership;
- the v0.27.0 backlog `plan.md`, implementation PRDs, tests, examples, and
  changelog as one series.

**Answer:** Agreed. Update every listed document in the same feature series.
Also update repository `AGENTS.md` so its messaging-platform term matches the
settled **Platform** language, and produce the separate Symphonai v0.27
adoption PRD. That PRD owns the directory source, System/Owner/Inbox Table Cache
adaptation, routing mode, environment behavior, and `context_id` keyword audit.

Examples, CLI templates, environment documentation, changelog, and migration
notes must stop teaching the removed custom credential store, `auto` routing,
the old webhook path, or implicit `WP_PHONE_ID` authority.

### 10f. Does Symphonai need its own adaptation PRD?

**My recommendation:** Yes. Keep it separate from the Wappa v0.27.0 PRDs.
Wappa ships the generic Table Cache `context_id`, the reserved System Scope,
the system-table builder, `InboxDirectoryTable`, and the persistent-source
contract. The Symphonai PRD should:

- replace its local `SYSTEM_SCOPE` and `build_global_table_cache()` workaround
  with Wappa's system-table builder;
- add an Owner-scoped Table Cache builder that passes `owner_id` as
  `context_id` without adding Owner to Wappa;
- keep normal Inbox builders passing `inbox_id` as `context_id`;
- review its `VersionedTableCache` call sites and classify each as System,
  Owner, or Inbox data;
- implement `IInboxDirectorySource` against Symphonai's database schema and
  connect it to Wappa's `InboxDirectoryTable`;
- keep one `META_APP_SECRET` declaration in Symphonai's process environment and
  let Wappa's settings adapter read it directly;
- do not add a second Wappa-specific App Secret field, copy the value into an
  alias, or pass an explicit `MetaApplicationConfig` while the
  environment-backed configuration is active. Symphonai's existing Marketing
  API settings may still read the original environment variable;
- keep `META_APP_ID` and `META_ADS_CONFIG_ID` under Symphonai's Marketing API
  configuration because Wappa does not consume them.

The `inbox_id` to `context_id` keyword rename needs a call-site audit. It does
not need a Redis data migration because the stored key values do not change.

**Answer:** Agreed. One separate Symphonai PRD owns Owner-scope adoption, the
consumer keyword migration, and the v0.27 Meta configuration handoff. Wappa
does not implement or define Owner. Symphonai declares `META_APP_SECRET` once
in the process environment; Wappa reads it without a duplicate Wappa-specific
settings field or handoff through Symphonai configuration.
