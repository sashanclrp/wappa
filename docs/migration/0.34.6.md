# Migrating from 0.34.5 to 0.34.6

This release makes shared identity, inbound projections, send evidence and discovery uniform across Platforms. The two clean cuts are universal message/context serialization and the explicit Meta configuration field. There are no aliases.

## Renamed and removed wire keys

These changes apply to `message.to_universal_dict()`, context `to_universal_dict()` and the `message` dictionary in built-in incoming SSE. Native models and `message.get_platform_data()` remain available for Platform-specific behavior. Existing Python text/selection/media accessors remain available.

| Family / Platform | Before | After |
| --- | --- | --- |
| Text / Instagram | `text` | `content` (WhatsApp already used `content`) |
| Selection / Instagram | `selection`, `text` | `selected_option_id`, `selected_option_title` |
| Template quick reply / WhatsApp | `button_payload`, `button_text` | `selected_option_id`, `selected_option_title` |
| Media / Instagram | `url`, `text`, `attachment_type` | `media_id`, `caption`, `media_family`; native attachment type is available through `get_platform_data()` |
| Reply context / Instagram | `reply_to_message_id` | `original_message_id` |
| Reply context / Instagram | `story_id`, `story_url`, extra native context fields | Read the native `context` through `message.get_platform_data()` |
| Reply context / WhatsApp | `platform`, `has_context`, `whatsapp_data` | Message-level `platform` and `has_context`; native context through `message.get_platform_data()` |
| Text, selection, media and reaction / WhatsApp | `whatsapp_data` (and all nested keys) | `message.get_platform_data()`; native data is absent from these universal projections |
| Image / WhatsApp | `has_caption`, `is_forwarded` | Test nullable `caption`; forwarding evidence is in the native accessor |
| Sticker / WhatsApp | `is_animated` | Read native sticker evidence through `get_platform_data()` |
| Reaction / WhatsApp | `is_adding_reaction`, `is_removing_reaction` | `is_removal` (invert for an added reaction) |

All text projections have `content`, `text_length`, `is_reply`, `is_forwarded`, nullable `is_frequently_forwarded` and the common message fields. All selections have `interactive_type`, `selected_option_id`, `selected_option_title`, nullable `original_message_id`, `is_button_reply`, `is_list_reply`, `is_quick_reply` and the common message fields. WhatsApp Template quick replies retain `message_type=button`; the selection keys are the same.

All media projections have `media_id`, `media_family`, historical `media_type`, nullable evidenced `mime_type`, `file_size`, `caption`, `filename`, `duration`, `dimensions`, `is_voice_message` and the common message fields. A media reference can be a native ID or a URL; pass it unchanged to `messenger.media.download`. Instagram webhook MIME is unknown (`mime_type=null`); use downloaded `MediaBytes.content_type` when resolved. `media_type` retains its historical nominal semantics and is not proof of MIME. No MIME constant or enum was removed.

Common message fields are `platform`, `message_type`, `message_id`, `sender_id`, `conversation_id`, `conversation_type`, `timestamp`, `processed_at`, `has_context`, `context`. Context is null when absent; otherwise it contains exactly `original_message_id`, `original_sender_id`, `is_reply`, `is_forward`. Missing IDs are null rather than omitted or empty strings. Instagram now includes the common conversation/context/processing fields on these projections. Story/share-specific message behavior remains Platform-specific.

## Renamed Python configuration parameter

Replace `MetaApplicationConfig(..., whatsapp_webhook_verify_token=SecretStr(...))` and reads of `.whatsapp_webhook_verify_token` with `MetaApplicationConfig(..., webhook_verify_token=SecretStr(...))` and `.webhook_verify_token`. The old constructor key fails validation. `META_WEBHOOK_VERIFY_TOKEN` and the settings environment adapter are unchanged. Diagnostics now describe Meta callbacks rather than WhatsApp-only trust.

## Host changes for identity and validation

1. Shared HTTP `recipient` and `addresses` preserve nonblank opaque strings. Phone/BSUID normalization moves to the selected adapter, matching Python `DirectMessage` sends. Do not depend on request-model construction to compact phones or uppercase BSUID prefixes. Shape-invalid WhatsApp addresses now reach adapter validation rather than shared-model 422 validation; local route violations return 400. Blank strings still fail shared validation. `RecipientIdentifier` remains available for explicitly WhatsApp-specific contracts; `RecipientRequest` consumers (including state-handler requests) now retain opaque addresses.
2. Prefer generic `InboxRef(platform=..., inbox_id=...)` and `PlatformAccountRef(platform=..., platform_account_id=...)`. Both installed Platforms also have matching `.whatsapp(...)` and `.instagram(account_id)` factories; no existing factory changed.
3. Use `user.identity(inbox_ref)`, `profile.identity(inbox_ref)` or `result.identity()` for the shared `UserIdentity`: Inbox Reference, existing recommended User ID, `addresses: DeliveryAddresses` and optional native/phone/BSUID/Parent/username evidence. Result projection needs an Inbox and recipient evidence. This introduces no reconciliation or historical merge policy. SSE adds nullable `identity` while preserving all existing envelope keys. Instagram IDs no longer populate `phone_number`; Parent BSUIDs no longer masquerade as phones. `classify_meta_identifier(value, platform=...)` accepts a Platform; its default retains the WhatsApp parser. Unknown shapes return no phone evidence.
4. Pass known addresses using `user.delivery_addresses()`; its additive `DeliveryAddresses.evidence` carries BSUID/Parent corroboration without making Parent evidence a fallback destination. Manually constructed targets can provide the same evidence. WhatsApp excludes a phone that equals the numeric suffix of a valid regular or Parent BSUID before I/O, then normalizes, deduplicates and orders remaining candidates. Proven echoes cease being attempted. Raw User/native evidence is retained. Host-known alias enrichment and same-subject checks stay Host-owned.

## Host changes for errors and send outcomes

`MessageResult.recipient_platform_id` carries native scoped recipient evidence. `MessageResult.error_evidence` and webhook `ErrorDetailBase.error_evidence` carry `ErrorEvidence(platform_code, platform_subcode, http_status, category, retry_safe, temporary)`. Both adapters retain native Graph code/subcode separately from the Wappa category: authentication, permission, messaging window, address rejection, rate limit, unknown outcome or other. Existing `error_code` values, including WhatsApp's `BSUID_RECIPIENT_NOT_SUPPORTED` tag and Instagram's `code/subcode` strings, are unchanged. Webhook `error_code` remains an integer. Migrate new logic to structured evidence instead of parsing historical codes or treating Graph code ranges as HTTP status ranges. `is_temporary_error()` now reads the evidenced temporary condition; `has_critical_errors()` uses neutral categories and `has_retryable_errors()` requires explicit retry-safe evidence. Temporary is never permission to retry. Unclassified retry safety is null; unknown outcomes explicitly disallow blind retries. Proven synchronous refusals can carry retry_safe=true, but aggregate evidence after partial acceptance is retry_safe=false; each failed part keeps its own classification.

Use `result.parts` (typed `MessagePart` values) and `result.aggregate_outcome` or `aggregate_message_outcome(result)` from `wappa.messaging`. Both survive normal JSON serialization. The aggregate adds `partially_accepted` to accepted/rejected/indeterminate/rate_limited; failed parts retain their outcome, `error_code`, structured error evidence and `retry_after`. Skipped parts remain `not_attempted`. Single WhatsApp sends have the same parts shape. Historical `message_outcome()` and its four-value enum are unchanged, so they must not be used to decide whole-call retries after a multipart send. Never resend an entire partially accepted or indeterminate call. Preserve the Host's admission, history and reconciliation policies. Native `platform_response` remains excluded from JSON; historical `wappa_parts` remains available there.

## Discovery

Use `messenger.discovery` (`MessengerDiscovery`) through the Messenger, pipeline or Platform Messenger. It describes `operations`, `media_operations`, `typing`, `read_scope`, `target_kinds`, typed `message_limits` and per-family `media_limits`. Qualifier `send_text:private_reply` identifies the operation that supports the extra target. Instagram read scope is thread; WhatsApp read scope is message. Instagram media supports upload/download, WhatsApp also supports info/delete. Media limits distinguish URL and upload extensions, MIME types, sizes and codec/content constraints. Wappa does not convert media.

`GET /api/{platform}/capabilities`, `/messages/limits` and `/media/limits` expose local registry discovery without Inbox lookup or provider I/O. Existing WhatsApp URLs and their historical limit keys are preserved; media limits add `formats`. Button/media operation names, `send_text:private_reply` and typed Platform-only Messengers are unchanged.

## Addendum: structured parts and recoverable expiry

`MessagePart.content: PartContent | None` is additive in both serialized `result.parts` and historical `platform_response["wappa_parts"]["parts"]`. Plain text has `content=null`. `PartContent` and its typed nested values are exported from `wappa.messaging`. Structures include buttons (neutral reply ID or URL), quick replies, carousel elements, media references (type and exactly one ID/URL), headers/footers, list sections/opener text, contacts, locations, data requests and native Template references/parameters. Snapshots describe the actual adapter payload after media selection/upload and emulation; rendered Template text is never invented. A video carousel on Instagram records the actual poster image and default URL action. Skipped planned parts can describe their plan, while a failed prerequisite upload has no invented media reference. Always filter `part.outcome == "accepted"` before adding `part.text` and `part.content` to accepted history. A refused buttons part must not enter history merely because its header part was accepted. Existing fields and outcome values are unchanged.

Redis expiry is now at least once across Wappa process restarts while Redis retains its data. Arming/renewal also writes a pending occurrence into the existing expiry database's `__system__:expiry:due` sorted set and `__system__:expiry:records` hash, with a generation and Redis-clock due time. Trigger key names and IExpiryCache signatures are unchanged. These index keys must be retained with the expiry database and excluded from any manual cleanup of application data. No new database, service or version change is required.

SchedulingPlugin(redis_expiry=True) recovers overdue entries whose TTL key is gone on startup and every two seconds, at most 100 admissions/in-flight indexed deliveries per process. Claims defer retries for 30 seconds; handler, binding and acknowledgment failures remain pending. Long or interrupted handlers can run more than once, so keep Host idempotent fences. A successful acknowledgment is generation-fenced and cannot erase a renewed occurrence. Cancel removes pending index data even after TTL expiry; its return value still counts TTL keys removed. Rebind retains the generation/due time of a live key and now also refuses a destination with pending overdue work. It still returns false when the source TTL key is gone. Already admitted work cannot be undone by cancel/renew/rebind.

The same ScheduledEvent/subject-binding/handler path is used. Indexed events add their original UTC `scheduled_for`, correlation `execution_id` generation, and `event.metadata["recovered"]` (true for index recovery, false for Pub/Sub), retaining `expired_key` and empty payload. Do not infer the User from an identifier or treat execution_id as an exactly-once guarantee. Raised unknown-action bindings are retried until the Host fixes the action or cancels it. The expiry source starts at priority 95 after ordinary capability/Host startup hooks; Pub/Sub reconnect limits do not disable index recovery.

Existing armed keys from before the upgrade have no index entry. Live notifications still work, but missed pre-upgrade expirations cannot be recovered. Re-arm pending keys that need the new guarantee; rebind of a still-live legacy key also indexes its remaining TTL. No KEYS scan, blanket backfill or armed-key migration is performed.
