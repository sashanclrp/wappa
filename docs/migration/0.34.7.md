# Migrating from 0.34.6 to 0.34.7

This release adds Wappa-owned migration tooling for live legacy Redis expiry timers and protects the recovery index from generic Wappa cache deletion, expiry and rename operations. No Host API rename or data-model change is required.

## Index existing timers without re-arming

Use this when timers were armed before 0.34.6 and are still alive. The command preserves the exact trigger value and remaining millisecond TTL. It adds an occurrence generation and original due time to Wappa's recovery index atomically. It never resets the timer, invents a new deadline or overwrites existing indexed work.

1. Stop old timer writers during cutover. Run before legacy timers expire: a key already gone without an index cannot be reconstructed. If upgrading from pre-0.34 unqualified namespaces, complete the cache-namespace migration first.
2. Supply the Redis URL explicitly. The command never infers it from an environment variable. The default database is the expiry database **3**, overriding any database in the URL; use `--database` for a custom expiry database.
3. Inspect a read-only dry run, then apply:

```bash
uv run wappa migrate expiry-index --redis-url "$REDIS_URL" --json
uv run wappa migrate expiry-index --redis-url "$REDIS_URL" --apply --json
```

The report contains counts only: `scanned`, `eligible`, `indexed`, `already_indexed`, `expired`, `persistent`, `invalid` and `conflict`. It prints no key names, identifiers, trigger values or connection credentials. SCAN uses bounded batches and validates qualified Inbox namespaces; it does not infer Platforms from raw account IDs. Only live string keys with positive TTLs and the Expiry Key shape are eligible. Persistent, invalid and vanished keys are skipped. Repeated apply runs preserve existing generations and due times. A concurrent renewal is already indexed and remains untouched; a key that expires before its atomic migration check is skipped.

Conflicting partial or malformed existing index records are left untouched and produce exit status 1, including on dry runs. Connection/storage errors produce exit status 2. The command is repeatable but not a database-wide transaction: a failed apply may already have indexed earlier valid keys. Fix the operational error and rerun; do not delete pending index data to make a report pass. Start the upgraded workers after migration. Their normal recovery source processes migrated occurrences when due, through the same scheduled hook.

## Retain the expiry database

Wappa's expiry database contains both trigger keys and these durable, non-expiring keys:

- `__system__:expiry:due`: sorted set of pending due times or temporary claim deadlines.
- `__system__:expiry:records`: occurrence generations and original due times.

Keep all three together in persistence, backups and restoration. Redis persistence must be configured for the Redis-restart/data-loss tolerance your deployment requires; Wappa does not enable AOF/RDB or change server configuration automatically. Use adequate capacity and a non-evicting deployment for durable timer work. Redis logical databases share server-wide memory and eviction policy: a separate database number alone does not protect the index from eviction. Wappa cannot recover data removed by eviction, FLUSHDB/FLUSHALL, a missing backup or manual raw Redis commands.

Wappa pool shutdown closes connections without deleting timer data. Generic Wappa key deletion skips the two reserved index keys, setting a TTL on them returns false, and renaming either reserved key raises ValueError. Ordinary cache cleanup still works. Cancel timers through `IExpiryCache.delete` / `delete_all_by_identifier`; these atomically remove the intended occurrence. Deleting a raw TTL key is not a supported substitute for cancellation.

## Optional Host recommendations: duplicate-safe business effects

Wappa supplies at-least-once expiry execution. Indexed occurrences carry `execution_id`, `scheduled_for` and `metadata.recovered`; retries retain the generation-based execution ID, while renewal creates a new occurrence. An execution ID is correlation, not an exactly-once guarantee. Legacy unindexed notifications have no durable generation.

For database-only business work, a Host can use `(Inbox Reference, action, execution_id)` as a unique occurrence key. Claim that key, apply business changes and record completion in one database transaction. A repeated invocation becomes a no-op. Roll back and let failures raise so Wappa can retry; do not mark completion before the work succeeds. Keep this ledger long enough for the Host's duplicate/replay policy.

For external effects, a Host can record an outbox intent in the same transaction, then deliver it with a provider-supported idempotency key where available. If the provider offers no deduplication guarantee, a crash after acceptance but before recording success leaves an uncertain outcome requiring reconciliation. A local processed flag or short lock cannot guarantee exactly one external send. Long handlers can outlive Wappa's 30-second claim and run concurrently in another worker, so use durable uniqueness/transactional fences rather than relying on that claim as a business lock.

These recommendations are optional Host design guidance; Wappa adds no business ledger, outbox schema or provider-specific exactly-once claim.
