# Migrating from 0.34.7 to 0.34.8

Instagram quoting is temporarily disabled. Keep passing `reply_to_message_id` through the same `IMessenger` calls: Instagram ignores it before I/O on text, media and interactive sends, including valid PrivateReply text sends. WhatsApp continues sending its native quote context. No signature changes or data migration are required. The recipient, content and ordinary split/emulation behavior remain unchanged. Inbound reply context and the original webhook `message_id` remain available.

A requested Instagram quote now records `platform_response["wappa_reply_to"] = {"dropped": true, "reason": "instagram_reply_quotes_disabled"}` and `reply_to_dropped=true` on the affected typed part. The old fallback `error_code` is no longer produced there: no quoted Graph attempt was made, so Wappa must not fabricate a Meta rejection. An actual unquoted send failure still returns its original provider error, without a quote retry. Consumers inspecting the old fallback evidence should read the suppression reason instead. Ordinary sends without a requested quote have no suppression evidence.

## Investigate IDs in the existing lab

The canonical manual probe is `scripts/instagram_reply_probe.py` in Wappa's repository and source distribution. The existing sibling `wappa_examples/instagram_conversations_example` lab exposes it as `app.reply_probe`. It bypasses adapter quote suppression deliberately for research; it is not a production send path. In the live lab run on 2026-11-08, Graph `graph.facebook.com/v26.0` accepted an unquoted control and rejected the exact inbound webhook ID and a fresh outbound send ID with `100/2534002`. A subsequent read-only history lookup confirmed that the Conversations API ID for the same command is identical to the rejected webhook ID. This supports temporary suppression on the tested route; it is not a claim about every Instagram account or Login mode. Evidence is recorded in the Instagram live-test plan.

For an interactive test, restart the existing lab and send `/reply` as an Instagram DM. Use Instagram’s Reply action when sending the command to include an earlier quoted-message ID. The lab compares normalized/raw webhook IDs, a sender/text/time-matched Conversations API ID and an accepted control send’s ID; equal candidates are tested once, without fallback, and the result reports errors or truncated history searches. Check visible quote rendering separately from API acceptance.

For the standalone manual probe, from the lab directory, supply the actual same-Inbox IGSID and fresh inbound webhook mid. The default is read-only: up to two Graph reads compare the supplied mid with up to 20 history message IDs, using lengths/fingerprints without printing IDs, tokens, content or raw error messages.

```bash
uv run python -m app.reply_probe --recipient-id '<IGSID>' --webhook-mid '<EXACT_MESSAGE_MID>' --api-version v25.0
```

The default Instagram Login path uses graph.instagram.com, IG_ACCOUNT_ID and IG_ACCESS_TOKEN from the lab environment. Match the version, account, host and token to the failing deployment; do not mix credentials or create/transform a mid from a prefix. For Facebook Login, select `--login facebook --page-id '<PAGE_ID>' --token-env META_REPLY_PROBE_TOKEN`; this selects graph.facebook.com and requires a matching Page token. Meta's supplied [Page-token reply example](https://developers.facebook.com/documentation/business-messaging/instagram-messaging/features/send-message#send-a-reply) does not by itself prove which ID the separate Instagram Login path will accept.

Only `--send` sends a message. Run one deliberate test at a time:

- `--send plain`: one plain control send.
- `--send webhook`: one quote attempt using the exact supplied webhook mid.
- `--send history:0 --expect-fingerprint '<FINGERPRINT_FROM_REPORT>'`: quote that history candidate only if its fingerprint still matches. A changed candidate stops before sending.

The probe never retries, falls back or sends a matrix automatically. Results report acceptance or HTTP/code/subcode facts without raw provider messages. A successful message_id proves provider acceptance, not visible quote rendering: check the recipient's app and record that separately. A different history ID is only a candidate until the live request and rendering are verified. An unavailable/ambiguous conversation or a failed read does not justify guessing another ID.
