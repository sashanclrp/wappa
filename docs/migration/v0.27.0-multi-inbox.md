# Migrating a Host Application to Wappa v0.27.0

v0.27.0 changes identity, credential ownership, callback authentication, Table Cache scope, environment behaviour, HTTP Inbox selection, and Host integration. Pick the path that matches your deployment and follow it in order. Do not mix variables from both paths in one process environment; Wappa fails startup when they mix.

Decisions behind every step are recorded in `docs/grill-me-sessions/260829_wappa-v0.27.0-multi-inbox-hardening.md`, [ADR-0010](../adr/0010-payload-routed-whatsapp-webhook.md), and [ADR-0011](../adr/0011-encrypted-inbox-directory.md). The runtime contract is in [`docs/public-contract.md`](../public-contract.md).

## Breaking public imports

| Removed | Replacement |
| --- | --- |
| `wappa.domain.interfaces.IInboxCredentialStore`, `InboxCredentials`, `InboxNotFoundError` | `wappa.domain.inbox.IInboxDirectorySource` (Host adapter), `wappa.domain.inbox.InboxNotFoundError` and siblings (typed failures). The internal resolver is not a Host extension point. |
| `wappa.domain.services.DatabaseInboxCredentialStore`, `WappaInbox`, `SettingsInboxCredentialStore`, `select_inbox_credential_store` | Wappa assembles the credential authority itself from the Inbox Routing Mode. There is no Host-replaceable directory and no prescribed SQL table. |
| `Wappa(inbox_credential_store=...)`, `Wappa.set_inbox_credential_store`, `WappaBuilder.with_inbox_credential_store` | `Wappa(inbox_directory_source=...)`, `Wappa.set_inbox_directory_source`, `WappaBuilder.with_inbox_directory_source` |
| `inbox_routing="auto"` | Only `legacy` (default) and `explicit` exist: `InboxRoutingMode` |
| `ITableCache` constructors and `create_table_cache(inbox_id=...)` | `context_id=` (positional calls keep working; the stale keyword raises `TypeError`). Stored keys do not change. |
| `POST /api/whatsapp/interactive/send-complex-buttons`, `/send-menu-list` | Removed from the HTTP contract. The demonstrations live in `wappa_full_example/app/handlers/interactive_demos.py`. |
| `OutboundRuntime.invalidate_inbox_credentials(inbox_id)` | Eviction is automatic after `InboxDirectory.refresh_inbox` / `deactivate_inbox`. `OutboundRuntime.evict_inbox(inbox_id)` remains for legacy out-of-band token changes. |
| `WhatsAppWebhookProcessor.validate_webhook_signature(payload, signature)` using the verify token | Requires `app_secret=SecretStr(...)`; Wappa's callback route performs this check itself. |

## Legacy single-Inbox Host

Nothing about your Inbox identity changes; the callback authentication and the Table Cache keyword do.

1. Keep `WP_ACCESS_TOKEN`, `WP_PHONE_ID`, and `WP_BID` as one complete bundle. A partial bundle fails startup.
2. Keep the default mode or set it explicitly: `Wappa(inbox_routing="legacy")` or `SYSTEM_INBOX_ROUTING_MODE=legacy`. Do not register an `IInboxDirectorySource`; legacy mode rejects it.
3. Add `META_APP_SECRET` (the Meta App Secret) next to `WP_WEBHOOK_VERIFY_TOKEN` in every environment that mounts the callback, including development. Wappa refuses to start the callback without both, and it rejects unsigned POSTs with `401`.
4. Change the Meta callback URL to `https://<host>/webhook/inboxes/whatsapp`. The old `/webhook/inboxes/{inbox_id}/whatsapp` and `/webhook/messenger/whatsapp/verify` return 404.
5. Replace any `ITableCache(inbox_id=...)`, `RedisTable(inbox=...)`, `MemoryTable(inbox=...)`, `JSONTable(inbox=...)`, or `create_table_cache(inbox_id=...)` keyword with `context_id=`. No Redis data migration is needed: the key values are unchanged.
6. Verify inbound and outbound traffic through the one configured Inbox. Your `/api/whatsapp/*` calls may omit `X-Wappa-Inbox-ID` (the configured Inbox is the default) or repeat it; any other value answers `404`.

Local webhook tools must sign the exact request body: `MetaCallbackAuthenticator(SecretStr(app_secret)).sign(body)` returns the `X-Hub-Signature-256` value.

## Explicit multi-Inbox Host

1. Remove `WP_ACCESS_TOKEN`, `WP_PHONE_ID`, and `WP_BID` from the process environment. Explicit mode fails startup if any of them is present.
2. Select explicit mode and configure encryption:

   ```text
   SYSTEM_INBOX_ROUTING_MODE=explicit          # or Wappa(inbox_routing="explicit")
   SYSTEM_TOKEN_ENC_KEY=<Fernet key>           # python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
   SYSTEM_TOKEN_ENC_PREVIOUS_KEYS=             # optional, ordered, comma-separated, rotation only
   META_APP_SECRET=<Meta App Secret>
   WP_WEBHOOK_VERIFY_TOKEN=<your chosen value>
   ```

3. Implement `IInboxDirectorySource` against your own durable schema. Both reads should use your primary database path; a replica accepts stale-credential risk on your side.

   ```python
   from wappa.domain.inbox import (
       IInboxDirectorySource, InboxRef, PlatformAccountRef,
       InboxCredentialRecord, parse_inbox_credential_record,
   )

   class MyInboxSource:  # satisfies IInboxDirectorySource (a Protocol)
       def __init__(self, db): self.db = db

       async def get_inbox(self, inbox_ref: InboxRef) -> InboxCredentialRecord | None:
           row = await self.db.fetch_inbox(inbox_ref.platform.value, inbox_ref.inbox_id)
           return parse_inbox_credential_record(row.wappa_record) if row else None

       async def list_inboxes_for_platform_account(
           self, account_ref: PlatformAccountRef
       ) -> tuple[InboxCredentialRecord, ...]:
           rows = await self.db.fetch_inboxes_for_waba(account_ref.platform_account_id)
           return tuple(parse_inbox_credential_record(r.wappa_record) for r in rows)
   ```

   Store the canonical record exactly as `dump_record_for_storage(record)` returns it (a JSON object), or map its fields into columns; the `access_token` envelope must be persisted verbatim and never decrypted.

4. Create encrypted records with Wappa's credential service **before** persisting them. Never build an envelope yourself.

   ```python
   app = Wappa(cache="redis", inbox_routing="explicit", inbox_directory_source=MyInboxSource(db))
   ...
   runtime = fastapi_app.state.inbox_runtime          # after build
   service = runtime.credential_service               # InboxCredentialService
   record = service.create_active_record(
       inbox_ref=InboxRef.whatsapp(phone_number_id),
       account_ref=PlatformAccountRef.whatsapp(waba_id),
       access_token=SecretStr(plaintext_token),
       credential_version=1,
   )
   await db.save(dump_record_for_storage(record))     # your transaction
   ```

   Rotation: `service.rotate_active_record(previous, access_token=SecretStr(new))` (version + 1). Deactivation: `service.create_inactive_record(previous)`. Key rotation: `service.rotate_encrypted_record(record)` returns the same record re-encrypted under the active key.

5. After every committed onboarding, rotation, WABA reassignment, or deactivation call Wappa's command so the directory and cached Messengers follow:

   ```python
   directory = runtime.directory                      # InboxDirectory
   await directory.refresh_inbox(InboxRef.whatsapp(phone_number_id))
   # or, after committing the inactive record:
   await directory.deactivate_inbox(InboxRef.whatsapp(phone_number_id))
   ```

   Both commands are idempotent and raise typed errors so an outbox or reconciler can retry them. `credential_version` must increase across the whole lifetime of an Inbox, including deactivation and recreation.

6. Send `X-Wappa-Inbox-ID: <phone_number_id>` on every Inbox-dependent Wappa HTTP operation (see the route matrix in the public contract). The header selects the Inbox Execution Context; it is not a credential. Your authentication and authorization decide whether the caller may use that Inbox, and they run first.
7. Configure one Meta App Secret and verify token per Wappa application. Wappa serves many WABAs and Inboxes under that App but never several Meta Apps.
8. Test WABA fan-out, phone-to-WABA membership mismatch (`400`), cache miss, deactivation, token rotation, directory outage (`503`), and two-Inbox isolation before cutover.

Explicit mode stores one encrypted bearer credential per Inbox record, even when several records contain the same physical Meta token.

## Encryption key rotation runbook

1. Generate a new key. Set `SYSTEM_TOKEN_ENC_KEY=<new>` and `SYSTEM_TOKEN_ENC_PREVIOUS_KEYS=<old>` on every deployment; new writes use the active key, reads accept both, and cache reads under the old key are rewritten under the new one.
2. Enumerate your durable rows and persist `service.rotate_encrypted_record(record)` for each. You never see plaintext.
3. Remove the old key only after every durable row has been re-encrypted and committed, every deployment reads the new key, at least 60 minutes (the maximum directory TTL) have passed since the last old-key cache write, and the rollout overlap window has ended.

Losing every accepted key makes the affected credentials unrecoverable.

## Callback cutover and rollback

1. Deploy the Host version that answers `/webhook/inboxes/whatsapp` with `META_APP_SECRET` configured.
2. Change the Meta callback URL and complete GET verification.
3. Send one real message to every active Inbox and confirm the correct handler, cache, credential, and reply sender.

Rollback needs **both** the previous package version and the previous callback URL; reverting only one stops delivery. Keep the previous package resolvable until acceptance ends.
