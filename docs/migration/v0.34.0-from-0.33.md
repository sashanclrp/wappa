# Upgrading from Wappa 0.33 to 0.34

0.34 makes Wappa a multi-Platform runtime: Instagram joins WhatsApp on one Messenger contract, one event lane per meaning, and one way to address a message. Most changes are breaking. Work through the steps in order; each ends with what to search for in your codebase.

Background: [ADR-0025](../adr/0025-messenger-contract.md) (one method per action, typed contracts), [ADR-0028](../adr/0028-whatsapp-first.md) (WhatsApp First), [ADR-0026](../adr/0026-inbox-connection.md) (connecting accounts), [ADR-0023](../adr/0023-inbound-webhooks.md) (echo lane), [ADR-0022](../adr/0022-inbox-identity-and-directory.md) (Delivery Addresses). Full detail per feature: [Instagram conversation contracts](instagram-conversation-contracts.md) and [CHANGELOG](../../CHANGELOG.md).

## 0. Deploy step: rename WhatsApp cache keys

0.34 qualifies every cache namespace, WhatsApp included: `whatsapp__<phone_number_id>` instead of the raw `phone_number_id`. Without this step, state, user, Inbox-scoped table and AI-state data and pending expiry timers written by 0.33 become invisible.

```bash
# 1. stop every 0.33 worker
# 2. dry run: lists every key it would rename
wappa migrate cache-namespaces -i <phone_number_id> -i <another_pnid> --redis-url "$REDIS_URL"
# 3. rename for real (keeps TTLs, never overwrites)
wappa migrate cache-namespaces -i <phone_number_id> -i <another_pnid> --redis-url "$REDIS_URL" --apply
# 4. start 0.34
```

- Name every WhatsApp `phone_number_id` you serve. The command never guesses, so Host-defined Table Cache scopes that happen to be numeric are left alone.
- JSON backend: add `--json-root <cache folder>`. The memory backend needs nothing.
- Pub/Sub subscribers must listen on `wappa:notify:whatsapp__<pnid>:*`.
- The Inbox Directory cache is not migrated: 0.34 clears it at startup and reloads each Inbox from your source on first use. If your Host changes a record while Wappa runs (token rotation, deactivation), call `await app.state.inbox_runtime.directory.refresh_inbox(inbox_ref)` after committing it.

## 1. Address every send with `DirectMessage` + `DeliveryAddresses`

0.33: `send_text(text, recipient="573001112233")`. 0.34: every recipient send takes `target=DirectMessage(...)`, and the target carries every address you know for the User.

```python
from wappa.messaging import DeliveryAddresses, DirectMessage

# Replying inside a webhook: let Wappa collect the addresses it proved.
target = DirectMessage(inbox_ref=self.inbox_ref, addresses=webhook.user.delivery_addresses())

# Outside a webhook (operator send, reminder, agent tool): pass what you stored.
target = DirectMessage(inbox_ref=inbox_ref, addresses=DeliveryAddresses.of(bsuid, phone))

await messenger.send_text("Hello", target=target)
```

- `DeliveryAddresses.of(...)` skips `None` and blanks and needs at least one address. Pass everything you have; do not choose an order.
- WhatsApp sends to the phone first, then the BSUID, and moves to the next address only when Meta rejects the address itself (`131030`, `131062`). Authentication Templates go to phones only. Do not write your own retry.
- `MessageResult.attempted_recipients` lists the addresses tried when Wappa fell back.
- `DirectMessage.recipient_id` still exists but is read-only (the first address).
- The Messenger never holds a recipient: build one Messenger per Inbox and pass a target per send. To message someone other than the webhook User, pass their target; there is no other way.
- A helper like `direct_target(messenger, user_id)` that wraps one string should take the User's addresses instead (or be replaced by `webhook.user.delivery_addresses()`), otherwise WhatsApp has nothing to fall back to.

Search: `recipient=`, `recipient_id=`, `DirectMessage(`, helpers that build targets.

## 2. Templates moved to the WhatsApp Platform Messenger

`send_text_template`, `send_media_template` and `send_location_template` left `IMessenger`. In a handler they are ready on `self.whatsapp.templates` (section 20).

```python
await self.whatsapp.templates.send_text_template("order_ready", target, params, "es", template_type="utility")
```

- Signatures are unchanged apart from `target`. Middleware still sees the same method names, so window guards keyed on `send_text_template` keep working.
- `OutboundRuntime.templates()` takes an `InboxRef`: `OutboundRuntime.from_app(app).templates(InboxRef.whatsapp(phone_number_id))`. A send on an Inbox without `ITemplateMessaging` returns `outcome=REJECTED`, `error_code="capability_unsupported"` before any I/O.
- Import `OutboundRuntime` from `wappa.messaging` (or `wappa.messaging.outbound_runtime`), never from `wappa.messaging.template_transport`. Build `InboxTemplateTransport` through `OutboundRuntime.templates`; its constructor now takes `inbox_ref` and `messenger_provider`.

Search: `.send_text_template(`, `.send_media_template(`, `.send_location_template(`, custom `IMessenger` fakes that implement them, `.templates(`, `template_transport import OutboundRuntime`, `InboxTemplateTransport(`.

## 3. Media download moved to the Media Library

```python
from wappa.messaging import MediaFamily

got = await self.messenger.media.download(webhook.message.media_id)
stored = await self.messenger.media.upload(Path("menu.png"), MediaFamily.IMAGE)
```

Search: `download_media(`, `media_handler.` used for downloads.

`IMediaLibrary` is the only media interface:

- `download(media_id, *, max_bytes=None)` bounds the read on both Platforms; an oversize read returns `rejected` with `error_code="SIZE"`. `upload(source, family, *, mime_type=None, filename=None)` takes a `Path` or raw `bytes` (name a `bytes` upload with `filename`) and passes an explicit MIME type to WhatsApp. `MediaFamily.STICKER` uploads a sticker (an image on Instagram).
- `info(media_id) -> ReadResult[MediaInfo]` and `delete(media_id) -> DeleteResult` replace `media_handler.get_media_info(...)` / `media_handler.delete_media(...)` in Platform-neutral code. Instagram has no such endpoint and raises `UnsupportedOperationError`; over HTTP, `GET /media/info/{id}` and `DELETE /media/{id}` answer 501 there.
- A custom `IMediaLibrary` must implement `info` and `delete` and accept `bytes` and `filename=` in `upload`.
- `wappa.domain.interfaces.IMediaHandler` is removed. Type WhatsApp-only media code (URL upload, tempfile, stream, limits) against the concrete `WhatsAppMediaHandler` (`wappa.messaging.whatsapp.handlers.whatsapp_media_handler`), reached as `WhatsAppMessengerAdapter.media_handler`.
- `wappa.messaging.IAttachmentMediaReader` and its capability lookup are removed, and with them the Instagram-only `stream(url)`. Replace `reader.get_bytes(url, max_bytes=n)` with `messenger.media.download(url, max_bytes=n)`.
- `GET /api/instagram/media/download/{media_id}` now serves the attachment (it answered 501); pass the attachment URL URL-encoded.
- `GET /api/whatsapp/media/download/{media_id}` maps the `ReadOutcome`: a Media ID Graph rejects as unknown, expired or deleted (Graph 400/404) or a CDN 404 answers 404, a Graph or CDN 401/403 (an expired Inbox token, say) answers 403, another CDN 4xx 400, an oversize read 413, and only a timeout, 5xx or transport error, on the info call or the CDN fetch, 503. Retry on 503 only; before, the status came from the error text (404 when it said "not found", else 400).
- `WhatsAppMediaHandler.get_media_info` and `download_media` report a failed Graph info call as `error_code="HTTP_<status>"` (`HTTP_400`, `HTTP_401`, `HTTP_503`, ...). `INFO_RETRIEVAL_FAILED` and `MEDIA_INFO_FAILED` now mean only a timeout or transport error; a Host that matched them to detect an unknown Media ID matches `HTTP_400` / `HTTP_404` instead.

Search: `IMediaHandler`, `IAttachmentMediaReader`, `.get_bytes(`, `.stream(`, `.get_media_info(`, `.delete_media(`, custom `IMediaLibrary` classes.

## 4. Move WhatsApp events to their new lanes

| 0.33 | 0.34 hook | Model |
| --- | --- | --- |
| `process_message` with `MessageType.EDIT` / `REVOKE` | `process_message_update` | `MessageUpdateWebhook` (`update_kind`, typed `message`) |
| `process_system_webhook` with `SystemEventType.SMB_MESSAGE_ECHO` | `process_outbound_echo` | `OutboundEchoWebhook` (`origin`, typed `message`, `get_text()`) |
| `process_system_webhook` with `HISTORY_SYNC` | `process_history_sync` | `HistorySyncWebhook` (`threads` of typed `HistoryMessage`) |
| `process_system_webhook` with `ACCOUNT_OFFBOARDED` / `ACCOUNT_RECONNECTED` | `process_inbox_connection` | `InboxConnectionWebhook` (`state`, `reason`) |

- `SystemEventType.SMB_MESSAGE_ECHO`, `HISTORY_SYNC`, `ACCOUNT_OFFBOARDED` and `ACCOUNT_RECONNECTED` are removed; code that references them fails at import. Move the logic.
- `OutboundEchoWebhook` only carries messages sent outside Wappa (Business app, Instagram app). Store them; never filter Wappa's own sends yourself.

Search: `SMB_MESSAGE_ECHO`, `HISTORY_SYNC`, `ACCOUNT_OFFBOARDED`, `ACCOUNT_RECONNECTED`, `MessageType.EDIT`, `MessageType.REVOKE`.

## 5. Replace raw payloads with typed models

- `SystemEventDetail.coexistence_payload` is removed: `smb_app_state_sync` is `contact_sync: ContactSync`; echoes and history moved to the lanes above.
- `group_update` is a `GroupUpdate`, `user_action` a `UserAction` (were dicts).
- `ad_referral` and `AdReferralBase` are removed: read `webhook.entry_referral` (`EntryReferral`, with `kind` = ad / post / link / other, plus the same ad fields) on every Platform. `has_ad_referral()` is now `is_from_ad()`.

Search: `coexistence_payload`, `ad_referral`, `group_update[`, `user_action[`.

## 6. Exhaustive code over `UniversalWebhook`

Six members were added: `MessageUpdateWebhook`, `IncomingCommentWebhook`, `MentionWebhook`, `OutboundEchoWebhook`, `HistorySyncWebhook`, `InboxConnectionWebhook`. Add cases to `match` / `isinstance` chains and to anything that serializes webhooks.

## 7. Custom Messengers, wrappers and test doubles

- Expose Templates or a Media Library by filling `self._capabilities = {ITemplateMessaging: self, IMediaLibrary: library}` in the constructor; the internal `IMessenger.capability()` lookup reads that mapping (default empty), keyed by interface only, and `messenger.media` and the Platform Messengers are built on it.
- `mark_as_read(message_id, target, *, typing=False)` takes a required `target`; `typing` is keyword-only (see section 14).
- `send_carousel(cards, target, body, reply_to_message_id=None)` is a new core method.
- `resolve_platform_user_profile(user: UserBase) -> PlatformUserProfile` is a new abstract method every Messenger implements. A fake or a Platform without a User lookup returns `PlatformUserProfile.from_evidence(self.platform, user)`; never raise for a Platform failure, return the evidence with the failure `outcome`.
- `send_audio(..., is_voice=False)` gained `is_voice` (voice note with waveform; WhatsApp needs OGG/Opus mono).
- `send_contact(contacts, target)` takes one typed `ContactCard` or a sequence (keyword renamed from `contact=`); wrap old dicts with `ContactCard.model_validate(d)`. `ContactCard.phones` is now optional (`None` when absent).
- `send_cta_message(..., header=)` takes an `InteractiveHeader | None` instead of a `str`: replace `header="Menu"` with `header=InteractiveHeader.of_text("Menu")`.
- `send_sticker(sticker_source, target)`: WhatsApp needs `.webp`, Instagram `.png`/`.jpg`/`.gif`. Pass both renditions (`["s.webp", "s.png"]`) and each Platform picks its own. A non-WebP sticker on WhatsApp now raises `ValueError` instead of failing later with status `131053`. Custom Messengers type `sticker_source` as `MediaRenditions`.
- Fakes that read `target.recipient_id` keep working; fakes that construct `DirectMessage(recipient_id=...)` must use `addresses=DeliveryAddresses.of(...)`.

## 8. Credentials and outbound sends outside webhooks

- Use `InboxCredentialAccess.from_app(app).resolve(inbox_ref)` instead of Wappa's internal resolver; resolve per operation, never cache.
- Send outside a webhook with `await OutboundRuntime.from_app(app).messenger(inbox_ref)`.

## 9. Middleware and events

- `SendInvocation.target` is the structured target; `SendInvocation.recipient` is its first address (`comment:<id>` for an Instagram private reply).
- `bot_reply` Pub/Sub notifications are keyed by the destination: a send to a User other than the webhook User is no longer announced under the webhook User.

## 10. Configuration

- Explicit Inbox routing still rejects `WP_ACCESS_TOKEN` / `WP_PHONE_ID` / `WP_BID` at startup. Apps that seed a WhatsApp Inbox from env in explicit mode must use their own variable names.

## 11. Unknown WhatsApp fields and schema drift

- A WhatsApp webhook `field` Wappa does not model and you did not register now reaches `process_system_webhook` as `SystemWebhook(UNSUPPORTED_EVENT)` with `event_detail.platform_event = {"field", "value"}`, and Meta gets 200. In 0.33 it was 400. Make sure your handler ignores or logs an event type it does not know.
- Unmodelled properties inside modelled Meta payloads are accepted. Wappa logs `META_SCHEMA_DRIFT platform=<p> field=<Model.field>` once per field per process, never the value. Alert on it and report the field upstream. `WHATSAPP_WEBHOOK_CONTRACT_DRIFT` no longer exists; remove alerts keyed on it.
- In your own test suite, set `WAPPA_STRICT_META_SCHEMA=1` so a fixture with a field Wappa does not model raises `MetaSchemaDriftError` instead of passing silently.

Search: `WHATSAPP_WEBHOOK_CONTRACT_DRIFT` in alert rules, `process_system_webhook` handlers.

## 12. The messaging HTTP API is Platform-neutral

- Routes are mounted at `/api/{platform}` ([ADR-0024](../adr/0024-outbound-http-routes-and-transports.md)). Your `/api/whatsapp/...` calls keep working; Instagram uses `/api/instagram/...` with `X-Wappa-Inbox-ID: <instagram account id>`.
- API sends now run your Messenger middleware (window guards, Pub/Sub `bot_reply`). Check that a guard meant only for bot replies does not block operator sends.
- Pass every address you hold: `{"recipient": "<phone>", "addresses": ["<bsuid>"]}`.
- Tests or tooling that read route paths see `/api/{platform}/...`. `create_whatsapp_router` is removed: mount `create_messaging_router`.
- Your own routes that depend on `get_inbox_execution_context` must live under a `{platform}` path parameter (no implicit WhatsApp).
- A route the Platform cannot serve answers 501: handle it like any other client error.
- Comments, post reads, history and private replies have routes now (Instagram); gate on 501 rather than on the Platform name.
- Route modules and profile classes have neutral names: import `MessagingRouteProfile`, `MessagingRouteCapabilities` and `RouteFamily` from `wappa.api.routes.families` (were `WhatsAppRouteProfile` / `WhatsAppRouteCapabilities` in `wappa.api.routes.whatsapp.route_families`), and `create_messaging_router` from `wappa.api.routes` or `wappa.api.routes.messaging_router` (was `wappa.api.routes.whatsapp_combined`). Shared route modules are `wappa.api.routes.<name>` (`messages`, `media`, `interactive`, `specialized`, `templates`, `state_handlers`); only the WhatsApp extension router stays in `wappa.api.routes.whatsapp`. OpenAPI tags dropped the `WhatsApp - ` prefix on shared routes.
- WhatsApp-only routes answer 501 under `/api/instagram`: `GET /messages/limits`, `/media/limits`, `POST /specialized/validate-contact`, `/specialized/validate-coordinates`, Template info and `/health` (the limits and validators used to answer 200 with WhatsApp data). Call them under `/api/whatsapp`. `GET /api/{platform}/interactive/limits` is shared and answers on both Platforms.
- `GET /api/whatsapp/health` returns only `status`, `platform`, `inbox_id` and `api_version`; read nothing else from it.
- Your own WhatsApp-only routes: replace `context.whatsapp_client()` with `client: WhatsAppClient = Depends(get_whatsapp_client)` from `wappa.api.dependencies.whatsapp_dependencies`, and gate them by mounting under a router with `dependencies=[Depends(whatsapp_only)]` (same module); `whatsapp_only(inbox_ref, feature)` is no longer a plain function in `wappa.api.dependencies.inbox_context`.

Search: `route_families`, `whatsapp_combined`, `WhatsAppRouteProfile`, `WhatsAppRouteCapabilities`, `routes.whatsapp.whatsapp_`, `whatsapp_client()`, `whatsapp_only(`, `/api/instagram/` calls to limits or validators, readers of `/health` `services`.

## 14. Neutral messaging values and a required `mark_as_read` target

The Messenger contract no longer imports WhatsApp types:

```python
from wappa.messaging import DirectMessage, InteractiveHeader, ListRow, ListSection, MessageResult

target = DirectMessage(inbox_ref=self.inbox_ref, addresses=webhook.user.delivery_addresses())
await self.messenger.mark_as_read(webhook.message.message_id, target, typing=True)  # was (id, typing=True)
await self.messenger.send_button_message(
    buttons, target, "Pro plan",
    header=InteractiveHeader.of_image(url="https://example.com/pro.png"),  # was InteractiveHeader(type=HeaderType.IMAGE, image={"link": ...})
)
await self.messenger.send_list_message(
    [ListSection(title="Menu", rows=[ListRow(id="a", title="A")])], target, "Pick", "Open",
    header="Menu",  # unchanged: list headers are text
)
```

- `mark_as_read` needs the target on every Platform, and `typing` must be passed by keyword. The HTTP `mark-as-read` body requires `recipient`.
- `InteractiveHeader` keeps every WhatsApp header kind: `of_text(text)`, `of_image(url=... | media_id=...)`, `of_video(...)` and `of_document(..., filename=...)`; the media is a `MediaRef` with a `url`, a `media_id` or both (WhatsApp sends the `media_id`, Instagram the `url`). `send_cta_message` takes the same `InteractiveHeader` (it took a `str`). HTTP `send-buttons` and `send-cta` take `header` as `{"kind": "text", "text": "Menu"}` or `{"kind": "video", "media": {"media_id": "123"}}`, instead of `{"type": ..., "image": {"link": ...}}` (buttons) or a string (CTA). HTTP `send-contact` takes `contacts: [...]` instead of `contact: {...}`.
- A carousel card's media is `MessageCard(header=CardMedia.image(url=...) | CardMedia.video(url=..., poster_url=...))`, by public URL only (WhatsApp card headers take a link, not a Media ID). On Instagram a video card needs `poster_url`; otherwise the send raises `UnsupportedOperationError` before any call.
- Interactive limits are the minimum across WhatsApp and Instagram and hold when you build the value (`ValidationError`), or, for `body`, `footer`, `button_text`, the list `header` and the section set, when you call the send (`ValueError`, before any Platform call). Several are stricter than WhatsApp alone: a list row title is at most 20 characters (was 24), a button or CTA body at most 640 (was 1024), a list body at most 1000 (was 4096), a carousel body at most 1000 (WhatsApp 1024), a card title and subtitle at most 80 each, and a card at most 2 buttons. A list allows 10 rows in total, not 10 per section, and row IDs must be unique across sections. A single section no longer needs a title; several sections each need one. Code that read `error_code` values such as `BODY_TOO_LONG` or `ROW_TITLE_TOO_LONG` from a failed button or list result catches `ValueError` instead.
- Instagram no longer rejects WhatsApp-valid input it can emulate: long text and captions are split into several messages, a media button header is sent first as its own message, and `disable_preview=True` is ignored.
- `MessageResult` lives in `wappa.domain.results` (also exported from `wappa.messaging` and `wappa.models`). Construct it with `platform=`; fakes that relied on the WhatsApp default fail validation. Read native evidence from `platform_response` instead of `api_response`.
- `webhook.whatsapp` is gone: read `webhook.user.phone_number`, `.bsuid`, `.parent_bsuid`, `.username`, `.country_code`.
- `PrivateReply(...)` no longer raises for a non-Instagram Inbox; the send still rejects it there.

Search: `mark_as_read(`, `send_cta_message(`, `send_contact(`, `MessageCard(`, `image_url=`, `card.phones`, `InteractiveHeader`, `HeaderType`, `BODY_TOO_LONG`, `ROW_TITLE_TOO_LONG`, `validate_buttons_menu_limits`, `max_rows_per_section`, `interactive_models import`, `basic_models import MessageResult`, `MessageResult(`, `api_response`, `from_response_payload`, `from_api_response`, `webhook.whatsapp`, `WhatsAppIncomingWebhookData`, `convert_header_to_dict`.

- Import `RoutedWebhookDelivery` and `PayloadRoutingError` from `wappa.core.inbound` (or `wappa.core.inbound.platform_webhooks`), not `wappa.core.inbound.webhook_routing`.
- `builder.mount_whatsapp_callback()` becomes `builder.mount_webhook_callback()`.
- A hand-built `FieldHandlerRegistry()` becomes `FieldHandlerRegistry(BUILTIN_FIELDS)` (`from wappa.platforms import BUILTIN_FIELDS`); `registry.get(field)` and `registry.fields()` take the Platform, and `field in registry` becomes `registry.get(field, PlatformType.WHATSAPP) is not None`. `register_webhook_field` requires `platform=` (section 18).

## 17. Send-route failures and the API event Platform

- `POST /api/{platform}/messages/send-text` and `/messages/mark-as-read` answer a 4xx when the Platform rejects the message, instead of 200 with `"success": false`. Callers that read `success` from a 200 must handle the error status (the body is `{"detail": "<error>"}`).
- Every send route maps a failed result the same way: the status its `error_code` maps to (413 size limits, 415 unsupported MIME type, 403 missing/unapproved Template), else 400. Specialized routes (`send-contact`, `send-location`, `send-location-request`) no longer guess 401/404/429/500 from words in the error text, and a Pydantic `ValidationError` raised while sending answers 400 instead of 422. Request-body validation is still 422.
- A failed send now also emits its API event (`process_api_message` with `response_success=False`) on every send route, as `send-text` already did.

## 20. Prebuilt Platform Messengers: `self.whatsapp`, `self.instagram`, `messenger.media`

Hosts never build or look up a capability. The runtime prebuilds them on every dispatch:

```python
async def process_message(self, webhook):
    target = DirectMessage(inbox_ref=self.inbox_ref, addresses=webhook.user.delivery_addresses())
    await self.messenger.send_text("Hi", target)                      # every Platform
    got = await self.messenger.media.download(webhook.message.media_id)  # every Platform
    if self.whatsapp is not None:                                     # WhatsApp dispatch
        await self.whatsapp.send_location_request("Where are you?", target)
        await self.whatsapp.templates.send_text_template("welcome", target, template_type="utility")

async def process_comment(self, webhook):
    await self.instagram.comments.reply_comment(webhook.comment_ref, "Thanks!")  # Instagram only
```

- `WappaEventHandler.whatsapp: WhatsAppMessenger | None` and `WappaEventHandler.instagram: InstagramMessenger | None` are new. Exactly one is set, matching the dispatch's Platform, wherever `self.messenger` is set (webhooks, Inbox-scoped crons, External Webhook Sources resolved to an Inbox); the other is `None`, and both are `None` without a Messenger.
- A Platform Messenger is the dispatch's `self.messenger` plus its Platform's extras; its `send_*` calls forward to `self.messenger`, so middleware runs as before. WhatsApp: `templates`, `send_location_request`, `send_contact_request`. Instagram: `comments` (`reply_comment`, `hide_comment`, `unhide_comment`, `delete_comment`, `set_comments_enabled`), `content` (`get_post`, `get_comment`, `list_comments`, `list_replies`, plus the mentioned-media reads) and `history` (`read_history`).
- `messenger.media` is the Inbox's `IMediaLibrary` on every Platform.
- Replace every Host-side lookup: `messenger.require_capability(IMediaLibrary)` → `messenger.media`; `require_capability(ITemplateMessaging)` → `self.whatsapp.templates`; `require_capability(IUserDataRequests).send_*_request(...)` → `self.whatsapp.send_*_request(...)`; `require_capability(ICommentControls)` → `self.instagram.comments`; `require_capability(IConversationContentReader)` → `self.instagram.content`; `require_capability(IConversationHistoryReader)` → `self.instagram.history`. Replace `capability(kind) is None` checks with `self.whatsapp is None` / `self.instagram is None`. `capability()` stays on `IMessenger` as an internal seam and is no longer documented Host API.
- Scores and services that received the Messenger and called `require_capability` take the Platform Messenger (`self.whatsapp`) beside it instead. Annotate with `from wappa.messaging.whatsapp import WhatsAppMessenger` / `from wappa.messaging.instagram import InstagramMessenger`.
- The concrete adapter classes are renamed, with no alias: `wappa.messaging.whatsapp.messenger.whatsapp_messenger.WhatsAppMessenger` → `WhatsAppMessengerAdapter` (also from `wappa.messaging.whatsapp.messenger`), and `wappa.messaging.instagram.messenger.InstagramMessenger` → `InstagramMessengerAdapter`. The old names now mean the Platform Messengers, which take one argument, the core Messenger. Tests that build an adapter directly rename the class; tests that bind a handler with `with_context(messenger=MessengerPipeline(adapter), ...)` get `self.whatsapp` / `self.instagram` automatically.
- A custom `PlatformEntry` may pass `build_platform_messenger=` (a callable that takes the core Messenger); `with_context(..., platforms=...)` takes the app's Platform Registry table. Fakes passed as `messenger=` to `with_context` need a `platform` attribute.

Search: `require_capability(`, `.capability(`, `WhatsAppMessenger(`, `InstagramMessenger(`, `whatsapp_messenger import WhatsAppMessenger`, `instagram.messenger import InstagramMessenger`.
